# Claude Codeで失敗した7つのパターンと回避法

---

## 最初に正直に言います

Claude Codeを使い始めた最初の2週間、私はほぼ毎日失敗してました。

「エラーが直らない」「指示通りに動かない」「気づいたら違うものができてる」。

同じ経験をしてる人、多いと思うんです。だからこそ、この記事を書きました。

---

## 自己紹介

佐伯亮です。沖縄在住の会社員で、副業でAI活用やアプリ開発をしています。

エンジニアではありません。プログラミングを独学で触り始めたのは2年前くらい。それまでは完全に文系の仕事をしていました。

Claude Codeを本格的に使い始めたのは、リリース済みのWebアプリ2本を作った後。「もっと効率よく開発できないか」と思ったのがきっかけです。

使い始めてから3ヶ月。失敗の数は軽く30回を超えました。

その中でも「同じミスを繰り返した」「これを知ってたら2時間無駄にしなかった」というパターンが、はっきりと7つあります。

今日はそれを全部書きます。

---

## Claude Codeって何？という人のために

ざっくり説明します。

Claude Codeは、Anthropicが作ったAIコーディングエージェントです。ターミナル（黒い画面）から使います。ファイルを読み書きして、コードを書いてくれて、コマンドも実行できる。

ChatGPTにコードを書かせるのと何が違うかというと、「実際にプロジェクトに触れる」点です。

コードを生成するだけじゃなくて、ファイルを作って、編集して、動作確認まで一連でやってくれる。開発の流れを丸ごと任せられる感覚に近いです。

ただ、その分「指示の出し方」が重要になります。ここを間違えると、ちゃんと動いてるのに全然違うものができあがります。

それが今日の本題です。

---

## 失敗パターン①：「とりあえず全部お任せ」

最初にやったミスがこれです。

「TODOアプリを作って」と一言だけ投げました。

Claude Codeは素直に動いてくれます。ファイルを作って、コードを書いて、「できました」と言ってくれます。

でも動かしてみると、自分が想像していたものと全然違う。

データの持ち方が違う。UIの構成が違う。使いたいライブラリが使われていない。

**回避法：** 最初に「仕様書」を書いてから依頼する。

「以下の仕様でTODOアプリを作って」という形で、使う技術スタック・機能一覧・データ構造を先に書き出します。5分かかりますが、後から2時間修正するよりはるかに早い。

---

## 失敗パターン②：CLAUDE.mdを作っていなかった

Claude Codeには `CLAUDE.md` というファイルを使えます。プロジェクトのルール・背景・制約を書いておくと、会話のたびに読み込んでくれる仕組みです。

私はこれを知らずに1ヶ月使いました。

毎回「このプロジェクトはReactを使っています」「スタイルはTailwindで統一してください」と説明し直す羽目になっていました。

計算してみたら、毎回の説明で1セッションあたり5〜10分のロスがあった。1ヶ月で20セッション以上やってたので、合計3時間以上を無駄にしてた計算です。

**回避法：** プロジェクト開始時に `CLAUDE.md` を作る。

```
# このプロジェクトについて
- 技術スタック：React + TypeScript + Tailwind CSS
- データベース：Supabase
- デプロイ先：Vercel
- コードスタイル：関数コンポーネントで統一
- コメントは日本語で書く
```

これだけでセッションのたびに説明する必要がなくなります。

---

## 失敗パターン③：エラーメッセージをそのまま投げ続ける

エラーが出たとき、最初はエラーメッセージをコピーしてそのまま貼り付けていました。

Claude Codeは丁寧に対応してくれます。でも、同じようなエラーが別の場所で再発することが多かった。

原因は「エラーだけ共有して、前後の文脈を渡していなかった」からです。

Claude Codeには「今何をしようとしていてエラーが出たのか」を含めて伝える必要があります。

**回避法：** エラーを共有するときの形式を決める。

```
【やろうとしていたこと】
Supabaseへのデータ挿入

【発生したエラー】
（エラーメッセージ）

【試したこと】
〇〇を変更してみたが変わらなかった
```

この形式で渡すようになってから、1発で解決する確率が体感で2倍くらいになりました。

---

## 失敗パターン④：大きな変更を一度に頼む

「ログイン機能を追加して、それからユーザーごとにデータを分けて、さらにプロフィールページも作って」

一度にこれを頼みました。

Claude Codeは頑張って全部やろうとします。でも途中でコンテキストが混乱したのか、既存のコードを上書きしたり、変数名が途中で変わったり、意図しない変更が積み重なります。

最終的に「何が変わったかわからない状態」になりました。

**回避法：** タスクを小さく切って、1つずつ確認しながら進む。

「まずログイン機能だけ追加して。完成したら次を指示します」という形が安全です。

変更が小さければ、何かおかしくなったときもすぐ気づけます。

---

## 失敗パターン⑤：git commitしないまま進める

これは本当に痛い目を見ました。

3時間作業して、Claude Codeに「全体的にリファクタリングして」と頼んだら、動かなくなりました。

どこで何が変わったかわからない。gitの履歴を見たら、最後のコミットが5時間前。

「戻せない」というパニックを経験したのは、これが最初で最後にしたいです。

**回避法：** 機能ひとつ追加するたびにコミットする。

Claude Codeに指示を出す前に「git add . && git commit -m 'before: 〇〇の機能追加前'」を習慣にしました。

これで「何かあったら戻れる」という安心感が生まれて、作業のスピードも上がりました。

---

## 失敗パターン⑥：「うまくいってるか確認せずに次へ進む」

Claude Codeが「実装しました」と言うと、つい信じてしまいます。

でも実際に動かしてみると動かない、ということが何度もありました。

特に「ブラウザで確認が必要な変更」をClaude Codeが目視で確認できないケース。

UIのレイアウト崩れ、非同期処理のタイミング問題、認証まわりの挙動など。

「できました」を鵜呑みにして5つ先の機能まで実装してから気づくと、どこで崩れたか追うのが大変になります。

**回避法：** 変更したら必ず自分でブラウザを開いて確認する。

当たり前のことですが、Claude Codeとの作業に慣れてくると「任せれば大丈夫」という油断が出てきます。

私は今も「実装したら必ずブラウザ確認」をルールにしています。

## 失敗パターン⑦：指示の「粒度」を間違える

有料パートに入ります。

最後の失敗パターンは、正直これが一番クリティカルでした。

「指示の粒度」というのは、どのくらい細かく・どのくらい大雑把に指示を出すか、という話です。

細かすぎても問題があります。大雑把すぎても問題があります。

どこがちょうどいい「粒度」なのか、3ヶ月かけて私がつかんだ感覚を説明します。

---

### 粒度が細かすぎると何が起きるか

「src/components/Header.tsx の45行目から52行目を以下のように書き換えて」

これを毎回やっていた時期があります。

コードを把握しきれてないと思って、細かく指示したほうが安全だと考えていたからです。

でも結果として、Claude Codeの「考える余地」をなくしていました。

全体の構成を理解したうえでいい実装をしてくれる能力があるのに、一行ずつ指示することで「言われた通りにだけ動くモード」になってしまう。

結果として、パーツは合ってるのに全体として動かない、という状況が発生しました。

---

### 粒度が大雑把すぎると何が起きるか

逆のパターンも経験しました。

「認証機能を実装して」これだけ。

Claude Codeは判断します。JWTを使うか、Supabase Authを使うか。セッション管理はどうするか。

そこで「自分のプロジェクトとは違う前提」で実装されることがあります。

後から気づいて修正するより、最初に「Supabase Authを使って、メールとパスワードで認証する機能を追加して」と書けばよかった。

---

### ちょうどいい粒度の見つけ方

私が今使っている基準は「機能レベルで指示して、実装の詳細はClaude Codeに任せる」です。

悪い例：「45行目のonClickハンドラを変更して」
良い例：「ログアウトボタンをクリックしたらSupabaseのセッションを削除してログインページに遷移する機能を追加して」

機能の「何をしたいか」は自分が書く。「どう実装するか」はClaude Codeが考える。

この分担がうまくいくようになってから、手戻りが体感で半分以下になりました。

## 実際に使っているプロンプトパターン

失敗パターンを7つ説明しましたが、ここからは「じゃあ実際どう指示を出してるか」をそのまま書きます。

---

### ① 機能追加のときのテンプレ

```
以下の機能を追加してください。

【機能名】
〇〇機能

【概要】
ユーザーが〇〇をすると、〇〇が起きる

【使用するもの】
- Supabase（既存のクライアントを使う）
- TailwindCSS（既存のスタイルと統一）

【考慮してほしいこと】
- エラーハンドリングを入れる
- ローディング状態を表示する

【触らないでほしいもの】
- src/lib/supabase.ts は変更しない
- 既存の認証フローは変えない
```

このテンプレに沿って書くだけで、意図通りの実装になる確率が上がりました。

---

### ② エラー対応のときのテンプレ

```
以下のエラーが発生しています。

【環境】
Next.js 14, TypeScript, Supabase

【やろうとしていたこと】
〇〇をしようとした

【エラー内容】
（エラーメッセージをそのまま貼る）

【関連するコード】
（エラーが発生しているファイルの該当部分）

【試したこと】
- 〇〇を確認したが変わらなかった

このエラーの原因と解決策を教えてください。
コードを変更する前に、原因の説明を先にしてください。
```

最後の「原因の説明を先に」が重要です。

いきなりコードを変えてもらうと、何が問題だったかわからないまま進んでしまいます。原因を理解してから修正してもらうほうが、次に同じエラーが出たときに自分で対処できます。

---

### ③ リファクタリングのときのテンプレ

```
以下のコードをリファクタリングしてください。

【対象ファイル】
src/components/〇〇.tsx

【リファクタリングの目的】
- 可読性を上げたい
- 重複しているロジックをまとめたい

【変えてほしくないこと】
- 外部から呼ばれているpropsのインターフェースは変えない
- 動作は現在と同じにする

変更箇所と、なぜその変更をしたかを説明してください。
```

「変えてほしくないこと」を明示するのがポイントです。

リファクタリングのつもりが、インターフェースまで変わって他の部分が動かなくなる、という経験をしてからこれを書くようにしました。

## CLAUDE.mdの実際の中身を公開します

私が今使っているCLAUDE.mdをそのまま載せます。

```markdown
# プロジェクト概要
Webアプリ（名称：〇〇）の開発プロジェクト

# 技術スタック
- フロントエンド：Next.js 14（App Router）、TypeScript、Tailwind CSS
- バックエンド：Supabase（データベース、認証、ストレージ）
- デプロイ：Vercel

# ディレクトリ構成の方針
- components/ : UIコンポーネント（ページロジックは含めない）
- app/ : Next.jsのルートとページコンポーネント
- lib/ : 外部サービスのクライアントと共通ロジック
- types/ : TypeScriptの型定義

# コーディングルール
- 関数コンポーネントで統一（クラスコンポーネントは使わない）
- カスタムフックはusePrefixで命名
- コメントは日本語で書く
- any型の使用は避ける

# 触らないでほしいファイル
- lib/supabase.ts（接続設定）
- middleware.ts（認証ミドルウェア）

# 作業の進め方
- 実装前に「何をするか」を一言説明してから進めてください
- 大きな変更をする場合は事前に確認してください
- 変更後は何が変わったかを箇条書きで教えてください
```

このファイルをプロジェクトのルートに置いておくだけで、毎回の説明が不要になります。

## 失敗から学んだ、Claude Codeとうまく付き合う3つの原則

7つの失敗パターンを振り返って、共通する教訓をまとめます。

**1. Claude Codeは「優秀なアシスタント」であって「読心術師」ではない**

伝えていないことはやってくれません。「察してほしい」は通じません。仕様は言語化する習慣が必要です。

**2. 小さく動かして、確認して、次へ進む**

大きなタスクを一気にやらせたくなる気持ちはわかります。でも失敗したときのリカバリコストが高すぎます。小さく積み上げるほうが結果的に早い。

**3. 失敗のコストを下げる仕組みを作る**

gitのコミット習慣、CLAUDE.mdの整備、テンプレートの作成。これらは最初の投資ですが、失敗したときのリカバリを格段に楽にしてくれます。

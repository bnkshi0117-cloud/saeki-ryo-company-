# Claudeのコンテキストウィンドウが長いと何が変わるか実験した

---

「200,000トークンって、実際どのくらい使えるの？」

Claudeを使い始めた当初、この数字が頭に引っかかってた。トークン数の話は色んなところで見るけど、「で、実際に何ができるの？」って具体的な話がなかなか見当たらない。

だから自分で試した。3週間かけて。

---

## そもそも、なぜコンテキストウィンドウを気にし始めたか

きっかけは仕事の資料整理だった。

沖縄の会社員として働きながら副業でアプリを作ってるんだけど、ある日「過去2年分のプロジェクト議事録を整理してレポートにまとめたい」という場面があった。

ファイルを全部合わせると、文字数にして約12万字くらい。

ChatGPTに突っ込もうとしたら、当然ながら途中で切れる。分割して処理するしかなくて、前後の文脈がバラバラになる。つまり「全部読んだ上でのまとめ」ができなかった。

そのとき初めて、コンテキストウィンドウの大きさが「作業の質」に直結することを実感した。

数値として「200Kトークン」と言われてもピンとこないけど、日本語でざっくり言うと「約15万〜16万字くらいの文章を一気に読める」くらいのイメージ。文庫本1〜2冊分が一発で入る計算になる。

---

## ChatGPTと何が違うのか、正直に比べてみた

比較が目的ではないけど、ここを避けると話がわかりにくいので書く。

GPT-4oのコンテキストウィンドウは128Kトークン。日本語だと大体8〜10万字くらい。十分大きいように見えるけど、実際に長い文書を複数扱い始めると、割とすぐ限界が来る。

Claudeの場合、現時点で200Kトークン（一部モデル）。体感で「もう少し入るかな？」と感じる余裕がある。

ただ、トークン数の差よりも、もっと大事なことがあった。

**「長い文章を読んだとき、どこまで覚えているか」**

これが、実験で一番気になった部分だった。

---

## 実験その1：10万字超えの文章を一気に読ませる

まず試したのは、自分が過去に書いたKindleの原稿4冊分のテキストをまとめて貼り付けること。

合計で約11万字。

プロンプトはシンプルにした。

「この4冊の原稿を全部読んで、各冊の主なテーマとキーメッセージを整理してください。また、4冊に共通して登場するテーマがあれば抽出してください。」

結果はかなり良かった。各冊の要約が的確で、自分でも気づいていなかった「4冊を通じた共通テーマ」を拾ってきてくれた。

驚いたのは、3冊目の中盤に出てきた具体的なエピソードを引用しながら「この話が4冊目の結論と繋がっています」と指摘してきたこと。

自分の文章なのに、「あ、確かに繋がってる」と思った。

ここで確認できたのは、少なくとも11万字の範囲では、前半の内容を後半の処理に活かせているということ。

---

## 実験その2：「途中で忘れる」問題を検証する

長文対応AIでよく言われるのが「先頭に入れた情報を後半で忘れる」という問題。いわゆる「位置バイアス」。

これを試すために、少し意地悪な実験をした。

1. 最初に「重要なキーワード」を10個埋め込む
2. その後、約9万字分の関係ない文章を挟む
3. 最後に「最初に言ったキーワードを思い出して」と聞く

結果、10個中8個は正確に答えた。残り2個は「〇〇のようなものでしたか？」と近い表現で返ってきた。

完璧ではないけど、「序盤の情報がほぼ消えない」という印象。

ちなみに同じ実験をChatGPT（GPT-4o）でやったとき、コンテキストが長くなるにつれて5〜6個しか出てこなかった。これはモデルの差というより、コンテキスト長の差が効いてる部分もあると思う。

---

## 実験その3：コードを大量に読ませる

アプリ開発でも試した。

自分が作ってるWebアプリのコードを丸ごと貼り付けて、「バグになりそうな部分と、改善できそうな部分を指摘して」とお願いした。

ファイル数は12個、合計行数は約2,400行。

これも一発で読んでくれた。

指摘内容が面白くて、「このファイルとあのファイルで変数名の命名規則が違います」とか「この関数、3箇所から呼ばれてるけど、引数の渡し方がファイルごとに微妙に違う」とか、個別ファイルを見てただけでは気づきにくい「横断的な問題」を見つけてきた。

コンテキストが長いことの強みは、まさにここだと思う。「全体を見た上での指摘」ができる。

## ここまで読んでくれた方へ

無料パートで伝えたかったのは、「コンテキストウィンドウが長い＝文章が長く書ける」じゃなくて、**「全体を見て考えられる」**ということ。

部分部分を処理するんじゃなく、全部を一度に把握した上でアウトプットできる。これが作業の質にどう影響するか、実感値がだいぶ変わると思う。

有料パートでは、この実験をもとに「実際どう使えば仕事に活かせるか」の具体的なワークフローを書いてます。

- 使った具体的なプロンプト全文
- 失敗したパターンと改善のポイント
- コンテキスト長を活かした自分の実際のワークフロー
- ChatGPTとClaudeを使い分ける基準

「実験結果を知る」だけで終わらせたくない方は、続きもどうぞ。

## 実際に使ったプロンプト全文を公開する

実験で使ったプロンプトをそのまま載せる。

### Kindle原稿まとめのプロンプト

```
以下は私が書いた4冊分の原稿テキストです。
各冊を「冊1」「冊2」「冊3」「冊4」のセクションに分けて貼っています。

[原稿テキスト全文]

これを読んで、以下を整理してください。

1. 各冊のメインテーマ（2〜3文で）
2. 各冊の読者へのキーメッセージ（箇条書き3個以内）
3. 4冊を通じた共通テーマ・思想（あれば）
4. 4冊をシリーズとして見たとき、何が「一貫していて」何が「ずれているか」

答えは日本語で、見出しをつけて整理してください。
```

このプロンプトのポイントは「4で矛盾や不一致を探す」と指定してること。長文の強みは「全体比較」なので、そこを意図的に引き出す聞き方にした。

---

### コードレビューのプロンプト

```
以下はWebアプリのコード全文です。
技術スタックはNext.js + TypeScript + Supabaseです。

[コード全文]

以下の観点でレビューしてください。

1. バグが起きそうな箇所（ファイル名と行番号を明記）
2. 複数ファイルをまたぐ一貫性の問題（命名、設計、型の扱いなど）
3. パフォーマンス上のリスク
4. 「直さなくていいけど気になる」程度のこと（低優先度）

厳しく指摘してください。「良い点」は聞いていません。
```

「良い点は聞いていません」と書いたのは、バランスを取ろうとして中途半端になるのを防ぐため。長文レビューほど「良い点と悪い点をバランスよく」になりやすいので、最初から排除した。

## 失敗したパターンと、その改善

実験の中でうまくいかなかったことも書く。

### 失敗1：何でも一気に入れればいいわけじゃない

最初は「入れられるだけ入れたほうがいい」と思って、関係ない情報も全部突っ込んでた。

たとえばコードレビューを頼むときに「会社のSlackのログ」とか「過去のメモ」まで含めてしまった。そうしたら出力がぼやけた。「コードの問題」と「チームのコミュニケーション問題」が混在したアドバイスになって、どれを優先すればいいかわからなくなった。

**改善：「何に集中してほしいか」と「それ以外は無視していい」を明示する。**

```
今回はコードの品質にだけ集中してください。
添付している会話ログはコンテキスト参考程度で、
そこへの言及は不要です。
```

この一文を入れるだけで、アウトプットの精度が上がった。

---

### 失敗2：長いと「後半になるほど雑になる」

これは体感としてある。コンテキストが長くなるほど、出力の後半部分が少し雑になることがある。

「4冊の比較をして」と頼んだとき、3冊目まではしっかりまとめてくれるのに、4冊目の記述が薄くなることがあった。

**改善：出力を分割してお願いする。**

一気に「全部まとめて」ではなく、

```
まず冊1と冊2についてだけ整理してください。
終わったら次のステップに進みます。
```

と段階的にやると、各ステップの精度が上がった。コンテキストは全部保持されたまま、出力だけを分割するイメージ。

---

### 失敗3：「長文を入れれば記憶する」は誤解

コンテキストウィンドウは「会話をまたいでの記憶」ではない。

新しいチャットを開いたら、前の会話は引き継がれない。「先週貼ったコードを覚えてる？」は通じない。

これは当たり前のことだけど、長文処理に慣れてくると錯覚しがち。「長い文章を読める＝記憶している」じゃなくて、「今の会話の中で処理できる範囲が広い」ということ。

**改善：重要な文書は毎回貼るか、プロジェクト機能を使う。**

ClaudeのProプランにはプロジェクト機能がある。ここにファイルを登録しておくと、毎回貼り直す手間が省ける。コンテキスト管理の実用的な解決策として、今は主にこれを使っている。

## コンテキスト長を活かした実際のワークフロー

実験を経て、今の自分の使い方に落とし込んだ話をする。

### ワークフロー1：「月次ふりかえり一括処理」

毎月、その月に書いたメモ・日記・タスクログをまとめてClaudeに投げる。

ボリュームは毎月だいたい4〜6万字くらい。

プロンプトは固定している。

```
以下は今月の記録です（日記・タスクログ・メモが混在）。

[全文]

これを読んで：
1. 今月よく取り組んでいたテーマ上位3つ
2. 繰り返し出てきたストレスや課題
3. 来月に引き継ぎたいこと
4. 記録から見えた「自分が本当に大事にしてること」

客観的な視点で整理してください。
自分では気づきにくい視点を優先して。
```

これが思いのほか使える。1ヶ月分を振り返るとき、自分で読み直すと2〜3時間かかるところが、このフローで30〜40分に縮まった。

---

### ワークフロー2：「副業プロジェクトの全体把握」

アプリ開発中に「いま自分が何をやろうとしてたか」を忘れることがある。

そういうときのために、プロジェクトのディレクトリをテキストで書き出して、Claudeに読ませる。

```
以下はプロジェクトのファイル構成とコード全文です。

[コード]

このプロジェクトが「現在どこまで進んでいて」「次に何をすべきか」を整理してください。
私はこのプロジェクトを久しぶりに開いた状態です。
```

「久しぶりに開いた状態です」という一文がポイント。状況を伝えることで、アウトプットのトーンが変わる。「前提をゼロから説明する」形式で返してくれるようになる。

## ChatGPTとClaudeを使い分ける基準

最終的に自分が落ち着いた使い分けを書いておく。

**Claudeを使う場面：**
- 長文を一括処理したいとき
- 複数のドキュメントを横断的に比較・分析したいとき
- コード全体のレビューをしてほしいとき
- 「全体を見た上での判断」が必要なとき

**ChatGPTを使う場面：**
- 画像生成（DALL-Eとの連携）
- ウェブ検索が必要なとき（リアルタイム情報）
- プラグイン・GPTsを使いたいとき
- 返答が短くていいとき（速度優先）

どちらが優れているかではなく、「その作業に何が必要か」で選ぶ。長文処理と全体把握が必要な作業はClaudeが向いている、という判断基準が今の自分の中にある。

---

## まとめ：明日から使えること

3週間の実験で学んだことを3つに絞る。

**1. 長文は「分割」じゃなく「全体投入」を試す**
部分的に分割して処理するより、全体を一気に入れたほうが「横断的な気づき」が出やすい。

**2. 「何を無視していいか」を明示する**
大量の情報を入れるときは、フォーカスしてほしいことと無視していいことを最初に書く。

**3. 出力は分割、入力は全部**
コンテキストは全部渡す。でも「答え」は一気に全部もらおうとしない。ステップを分けると精度が上がる。

コンテキストウィンドウの長さは、ただの「器の大きさ」じゃない。使い方次第で、「考える質」が変わる。これが3週間やってみて一番感じたことだった。

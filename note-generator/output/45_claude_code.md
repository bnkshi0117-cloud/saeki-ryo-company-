# Claude Codeの料金を1ヶ月で使い切った話と反省

---

## 正直に言います。やらかしました。

Claude Codeのサブスクに入ったその月、上限まで使い切りました。

「どんだけ開発したんだよ」って思う人もいるかもしれないけど、実態は違います。**無駄なトークンをひたすら消費していただけ**でした。

同じ失敗をしてる人、絶対いると思って書きます。

---

## Claude Codeを始めた経緯

去年の秋ごろ、仕事終わりにWebアプリを作り始めました。

沖縄でふつうに会社員をしながら副業でアプリ開発をやってるんですが、コードは「なんとなく読める・少し書ける」くらいのレベルです。独学でPythonをかじった程度。

以前はChatGPTに「このコード書いて」って頼んで、自分でVSCodeに貼り付けて、エラーが出たらまたChatGPTに聞いて……という作業を繰り返していました。

これが地味にしんどい。コードとAIの画面を往復し続ける感じ。

そこでClaude Codeの存在を知りました。

「ターミナルからClaudeに指示を出したら、コードを書くだけじゃなくてファイルの作成・編集・実行まで全部やってくれる」という触れ込みで。

**「これは絶対楽になる」と思って即課金しました。**

---

## 最初の1週間は本当に感動した

セットアップはそこまで難しくなかったです。

Node.jsを入れて、`npm install -g @anthropic-ai/claude-code`してAPIキーを設定して、プロジェクトのフォルダでターミナルを開いて`claude`と打つだけ。

最初にReactのシンプルなタスク管理アプリを作ってみたんですが、これが面白いくらいサクサク動く。

「サイドバーにカテゴリー一覧を出して、クリックしたらそのカテゴリーのタスクだけ表示されるようにして」

そう入力したら、数十秒でコードが書き換わって、ターミナルに変更内容が流れて、ブラウザを更新したら実装されてる。

最初の数日は「これすごい」という感動だけで動いていました。

---

## 2週目から雲行きが怪しくなってきた

問題が起き始めたのは、アプリの規模が少しずつ大きくなってきてからです。

「なんかエラーが出てるんだけど直して」
「やっぱりUIをこっちのデザインに変えたい」
「あ、でもさっきの機能も残して」
「全体的にもっとシンプルにしたい」

こういう**あいまいな指示を何度も投げ続けていました。**

Claudeは真面目に答えてくれます。毎回丁寧に、変更内容を説明しながらコードをいじってくれる。

でも結果的に何が起きていたかというと。

- 同じようなエラーを何度も修正させていた
- 一度消した機能をまた追加させていた
- 全体像を伝えずに部分的な修正を繰り返していた
- 「ちょっと確認したい」だけのために長い質問をしていた

**1回の会話で使うトークン量を全く意識していませんでした。**

---

## 月末に請求を確認して絶句した

使用量の確認方法を知ったのが月末近く。

Anthropicのダッシュボードを開いたら、APIの使用量グラフが右肩上がりで上限に張り付いていました。

金額にすると、自分が契約していたプランの上限ギリギリ。

「え、これ全部自分のアプリ開発に使ったやつ？」

振り返ってみると、**完成したものはほぼゼロ**でした。

動くコードはあるけど、あちこちいじりすぎてバグが増えて、修正のためにさらにClaudeに頼んで……という負のループに入っていた。

作業ログを見返したら、3週間で20本以上の「会話セッション」が残っていました。1セッションで1つのことを解決するどころか、あちこちに話が飛んでいた。

---

## 何がまずかったか、整理してみた

冷静に分析すると、失敗の原因は3つありました。

**① 指示があいまいすぎた**

「なんかいい感じにして」「シンプルにして」「もっと使いやすく」

これ、人間に頼むときも困る指示ですよね。Claudeも毎回ベストを尽くしてくれるけど、方向性がズレたまま修正を繰り返すことになる。

**② 設計を先にやっていなかった**

コードを書く前に「何を作るか」「どういう構成にするか」を決めていなかった。

頭の中でぼんやりとしたイメージだけ持って、「とりあえず作って」という感じでセッションを始めていた。だから途中で「やっぱりこうしたい」が何度も出てきた。

**③ CLAUDE.mdを使っていなかった**

これが一番もったいなかった。

Claude Codeには`CLAUDE.md`というファイルをプロジェクトに置いておくと、毎回の会話で自動的に読み込んでくれる機能があります。

プロジェクトの概要、使っている技術スタック、コーディングのルール、これまでの決定事項……これを最初から書いておけば、毎回同じ説明をしなくて済む。

でも自分は最初の1ヶ月、このファイルの存在をちゃんと活用していませんでした。

毎回「このアプリはReactで作っていてSupabaseをDBに使っていて……」から説明し直していた。**完全な無駄でした。**

---

## 翌月から変えたこと

失敗から学んで、2ヶ月目は使い方を根本から変えました。

結果として、**同じ作業量でトークン消費が体感で半分以下**になりました。

具体的に何を変えたか。それを有料パートで詳しく書きます。

- CLAUDE.mdの実際の中身と書き方
- 「1セッション1タスク」の原則と運用方法
- 指示の出し方テンプレート（自分が実際に使っているもの）
- エラー対応でトークンを無駄にしないコツ
- 事前設計に使っているシンプルなフォーマット

同じ失敗をこれからする人が減れば、この記事を書いた意味があります。

## 翌月から実際にやったこと【具体的な改善策】

### 改善①：CLAUDE.mdを最初に作る

これが一番インパクトが大きかった改善です。

`CLAUDE.md`はプロジェクトのルートディレクトリに置くだけ。Claude Codeが自動で読み込んでくれます。

自分が実際に使っているテンプレートはこんな構成です。

```
# プロジェクト概要
このアプリは〇〇を目的としたWebアプリです。
ターゲットユーザー：〇〇
主な機能：〇〇、〇〇、〇〇

# 技術スタック
- フロントエンド：React + TypeScript
- バックエンド/DB：Supabase
- デプロイ：Vercel
- スタイリング：Tailwind CSS

# コーディングルール
- コンポーネントはsrc/components/に置く
- 型定義はsrc/types/に集約する
- コメントは日本語でOK

# 現在の状態
- 認証機能：完成
- タスク一覧表示：完成
- タスク追加：作業中
- 未実装：タスク編集、削除

# 決定済み事項
- カラーはblue-600をメインカラーとして使う
- モバイルファーストで設計する
```

このファイルを置いておくだけで、毎回「このプロジェクトは……」という説明が不要になります。

**体感として、1セッションあたりの最初のやり取りが3〜4往復減った**感じがします。これが積み重なるとかなりのトークン節約になります。

---

### 改善②：指示を出す前に「一文メモ」を書く

以前は思いついたことをそのままターミナルに打ち込んでいました。

今は指示を打つ前に、必ずメモ帳に一文書いてから送るようにしています。

**悪い指示の例：**
```
なんかダッシュボードページが重い感じがするのと、
あとデザインもちょっと古い感じがするから
改善してほしいんだけど、でも今のレイアウトは変えないで
```

**改善後の指示の例：**
```
ダッシュボードページのロード時間を改善してください。
原因の特定と修正案の提示をまずお願いします。
（デザイン変更は今回のスコープ外です）
```

ポイントは「1つの指示に1つのタスク」。

デザインの改善とパフォーマンスの改善は別セッションでやる。一度に複数を頼むと、Claudeの返答も長くなるし、途中で方向性がぶれやすくなります。

---

### 改善③：エラー対応の手順を決める

1ヶ月目に一番トークンを無駄にしていたのが、エラー対応です。

エラーが出るたびに「エラーが出ました」とメッセージをそのまま貼り付けていた。

改善後は以下の手順を守るようにしました。

**ステップ1：エラーメッセージを自分で読む（30秒）**

意外とエラー文に解決策が書いてあることが多い。`Module not found`なら`npm install`するだけとか。

**ステップ2：エラー行のコードを確認する（1分）**

どのファイルの何行目でエラーが出ているか確認する。

**ステップ3：Claudeに渡す情報を整理してから送る**

```
以下のエラーが発生しています。

【エラーメッセージ】
（エラー文をそのままコピー）

【発生箇所】
src/components/TaskList.tsx の45行目

【やろうとしていたこと】
タスクの削除ボタンを押したときに一覧を更新する処理を追加した

【試したこと】
useState の更新方法を変えてみたが同じエラーが出た
```

この形式にしてから、1〜2往復でエラーが解決するようになりました。

以前は「エラーが出た→Claudeが確認→追加情報を求められる→また確認」という4〜5往復を繰り返していた。

---

### 改善④：開発前の設計に30分かける

これが一番地味だけど一番効いた改善です。

コードを書く前に、紙かNotionに以下を書き出すようにしました。

- 今日作る機能は何か（1つに絞る）
- その機能の入力と出力は何か
- どのファイルを変更するか
- 完成の定義は何か

たとえば「タスクの編集機能を追加する」というタスクなら：

- 入力：編集ボタンをクリック → モーダルが開く → テキストを変更 → 保存ボタン
- 出力：DBが更新される、一覧が更新される
- 変更するファイル：TaskList.tsx、TaskEditModal.tsx（新規）、supabase/tasks.ts
- 完成の定義：編集後に一覧に反映されること、キャンセルも動作すること

これを先に決めておくと、Claudeへの最初の指示が格段に明確になります。

「タスクの編集機能を追加します。編集ボタンでモーダルを開き、変更後にSupabaseのtasksテーブルを更新する実装をお願いします。関係するファイルは〇〇です」

この指示なら、最初の返答でほぼ正しい方向のコードが来ます。

---

### 改善⑤：セッションの終わりにCLAUDE.mdを更新する

1セッション終わったら、5分だけ時間を取ってCLAUDE.mdを更新します。

「今日完成したこと」「今日決めたこと」を追記するだけ。

たとえば：

```
# 更新履歴（2024年11月）
- タスク追加機能：完成（TaskForm.tsx）
- タスク一覧のページネーション：完成（1ページ10件）
- 編集機能：作業中
```

これがあることで、次のセッションでClaude Codeが現在の状態を正確に把握できます。

「どこまで出来てましたっけ」という確認のための無駄なやり取りがなくなります。

---

## 2ヶ月目の結果

改善後の2ヶ月目。

APIの使用量は1ヶ月目と比べて、**金額ベースで約40%減**でした。

作業量は増えていたのに。むしろアプリの機能は倍以上になっていました。

減ったのはトークンだけじゃなくて、作業のストレスも減りました。

「またうまく伝わらなかった」「また同じエラーが出た」というイライラが明らかに少なくなった。

Claude Codeは優秀なツールですが、**使う側の準備と指示の質で全然違う結果が出る**というのが正直な感想です。

---

## まとめ：Claude Codeを始める前にやること

最後に整理します。

Claude Codeを始めるなら、最初にやることはこれだけです。

1. **CLAUDE.mdを作る**（プロジェクト概要・技術スタック・現在の状態を書く）
2. **1セッション1タスクを守る**
3. **設計を先にやる**（30分の投資で何時間もの無駄を防げる）

自分が1ヶ月目にやらかした失敗は、全部「準備不足」と「あいまいな指示」に集約されます。

ツールの性能に期待しすぎて、使う側の準備をおろそかにしていた。

Claude Codeは本当に便利なツールです。ただ、便利さを引き出すのは結局、使う側の指示の質だと思います。

これからClaude Codeを使い始める人や、「なんかうまく使えてない」と感じてる人の参考になれば。

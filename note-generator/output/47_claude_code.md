# Claude Codeで個人開発を始めてリリースまで何時間かかったか

---

## コードが書けなくても、アプリは作れる。本当に。

最初にこれを聞いたとき、正直「また誇張でしょ」と思いました。

でも、実際にやってみたら本当にできた。しかも思ったよりずっと早く。

沖縄でサラリーマンをしながら副業でアプリ開発をしている佐伯です。今回は「Claude Codeを使った個人開発の全記録」として、アイデアを思いついてからリリースまで何時間かかったか、包み隠さず書きます。

---

## 自分のスペックを先に明かしておく

まず「非エンジニア」と言っても程度がありますよね。

私のスペックはこんな感じです。

- 文系出身、プログラミング学習歴は独学3年ほど
- PythonとJavaScriptは「なんとなく読める」レベル
- フレームワークは触ったことある程度（Reactは怖くて避けてた）
- GitHubのコミットは人並みにできる
- VercelやSupabaseは名前は知ってる

要するに「ゼロではないけど、ひとりで実務レベルのアプリは作れない」人間です。

以前にWebアプリを2本リリースしたとはいえ、どちらも相当な時間をかけました。ひとつは3ヶ月、もうひとつは2ヶ月近くかかっています。

それがClaude Codeを使ったら、どう変わったか。

---

## 今回作ったもの

作ったのは「沖縄の飲食店レビューを音声で残せる簡易ツール」です。

地元で食べ歩きをするのが好きで、行った店のメモをスマホで音声入力してそのままAIが整形してくれる、というシンプルなWebアプリ。

機能としては：

- 音声入力 → テキスト変換
- AIによる整形（お店名、評価、コメントの形に自動整理）
- ローカル保存（ブラウザのIndexedDB使用）
- シンプルな一覧表示

バックエンドなし。フロントエンドのみ。

「シンプルすぎる」と思うかもしれませんが、これが個人開発のコツだと最近わかってきました。最初はとにかくMVP（最小限の動くもの）を作ることが大事。

---

## Claude Codeとは何か、簡単に説明する

使ったことない人のために軽く説明します。

Claude CodeはAnthropicが提供しているAIコーディングエージェントです。ターミナルから起動して、自然言語で指示を出すとコードを書いてくれる。

ChatGPTのコード生成と何が違うかというと「自律的にファイルを操作する」点です。

ChatGPTは「コードを出力」してくれる。

Claude Codeは「コードを書いてファイルに保存して、エラーがあれば自分で直す」。

この違いはかなり大きい。コードをコピペする手間がなく、エラーループも自動で処理してくれることが多い。

課金プランはClaudeのProプラン（月20ドル）が必要です。API課金になる場合もあります。私はProプランで使っています。

## 開発スタートから最初の1時間

Claude Codeをターミナルで起動して、最初に出した指示は日本語でこんな感じ。

「沖縄の飲食店レビューを音声で記録するシンプルなWebアプリを作りたい。フロントエンドのみで、音声入力からテキストに変換して、AIで整形して保存できるものを作ってほしい。技術スタックはHTML、CSS、バニラのJavaScriptで。まずはファイル構成だけ提案して」

最初からガッと作らせるのではなく、構成の提案から始めさせる。

これが私なりのコツで、いきなり「全部作って」と言うと収拾がつかなくなることがある。

Claude Codeが返してきた構成：

```
/
├── index.html
├── style.css
├── app.js
├── api.js
└── storage.js
```

シンプル。これで十分でした。

「OK。このファイル構成で進めて。まずindex.htmlとstyle.cssを作って」と返すと、30秒ほどで両方のファイルを生成してくれた。

ブラウザで開くと、ちゃんとデザインが当たっている状態で表示された。

このとき少し感動しました。「え、もうUI出てる」と。

## 詰まったのはここ

順調に見えますが、もちろん詰まる部分はありました。

**詰まりポイント①：Web Speech APIのブラウザ互換性**

音声入力にブラウザ標準のWeb Speech APIを使うつもりだったんですが、SafariとFirefoxで動かない。

Claude Codeに「Safariでも動くようにして」と伝えたら、最初は「polyfillを入れる」という方向で修正してきた。でも実際試したら動かなかった。

この問題、Claude Code自身も2回ほど試行錯誤していました。ターミナルで自動修正が走って、また失敗して、また修正して……という様子がリアルタイムで見えるのは面白い体験でした。

結局「iOS Safariでは音声入力を使えない旨をユーザーに表示する形にして」という方向転換を私がして、そこからはスムーズでした。

ここで30分ほどロスした。

**詰まりポイント②：AI整形部分のAPI連携**

音声テキストをClaude APIに投げて整形する部分で、APIキーの扱いに迷いました。

フロントエンドのみの構成だとAPIキーがユーザーに見えてしまう。これはセキュリティ上よくない。

「フロントエンドのみでAPIキーを安全に扱う方法はあるか」とClaude Codeに聞いたら、「ない」と正直に返してきた。

「では、ユーザーが自分のAPIキーを入力して使う形式にする」と方針転換。

Claude Codeに指示を変えて「ユーザーがAPIキーをローカルに保存して使う形に変更して」と伝えたら、10分で実装してくれました。

この方針転換自体も、Claude Codeと対話しながら決めた。これが「壁打ち相手」として使えるということ。

## トータル何時間かかったか

結論を先に書くと、**企画から初回デプロイまで6時間半**でした。

内訳はこんな感じ：

- 企画・要件整理：30分
- Claude Codeとの開発（コーディング）：3時間
- バグ修正・調整：1時間
- Vercelへのデプロイ設定：30分
- 動作確認・微調整：1時間
- README作成・公開準備：30分

以前なら同じものを作るのに2〜3週間かかっていたと思います。

コーディングの3時間も、自分でゼロから書いていたわけではなく、Claude Codeに指示を出しながら確認している時間がほとんど。

純粋に「自分がコードを書いた」時間は、細かい修正の20〜30分程度。

## 「使えない」と感じた瞬間も正直に書く

Claude Codeが万能かというと、そんなことはありませんでした。

**①複雑な要件を一度に伝えると迷走する**

「音声入力して、AIで整形して、カテゴリ分けもして、地図と連携して……」と欲張った指示を出したとき、ファイルが肥大化してわけわからない状態になりました。

途中で「全部リセットしてシンプルな要件だけで作り直して」と伝えて仕切り直した。

この経験から「機能は削ぎ落とすほどいい」と改めて実感しました。

**②ライブラリのバージョン問題**

古いバージョンの書き方でコードを生成することがある。エラーが出て、原因を調べたらdeprecatedなメソッドを使っていた、というケースが1回ありました。

「最新バージョンで動くように書いて」という一言を最初に入れるようにしています。

**③「なぜそうなったか」の説明が長い**

Claude Codeはコードを書きながら説明もしてくれるんですが、説明が長すぎて読む気が失せることがある。

`--dangerously-skip-permissions`フラグは使わず、必要に応じて「説明は短く」と追加指示するようにしました。

## 実際に使ったプロンプトを全部公開する

### 開発開始時の「設計プロンプト」

まず最初に使ったのがこれです。

```
これから[アプリ名]を作ります。
用途：[一行で説明]
ターゲットユーザー：[具体的に]
使用技術：[スタック]
制約：[バックエンドなし、など]

まずはファイル構成だけ提案してください。
コードはまだ書かなくていいです。
```

ポイントは「まずファイル構成だけ」という制限を入れること。

最初から「全部作って」と言うと、Claude Codeはすごい勢いでファイルを生成し始めます。後から「やっぱりこうしたい」となったときの修正コストが跳ね上がる。

設計段階でYes/Noを決めてから実装に入ると、ブレが少なくなります。

---

### 機能を一個ずつ実装させるプロンプト

```
前のファイル構成をベースに、[機能名]を実装してください。
他の機能にはまだ手をつけないでください。
完成したら「この機能の実装が完了しました」と報告してください。
```

「他の機能には手をつけない」という一文が重要。

Claude Codeは親切なので、関連する他の部分も先回りで修正してくれることがある。悪意はないのですが、意図しない変更が入ると混乱します。

スコープを絞った指示を出すことで、管理しやすくなりました。

---

### エラーが出たときのプロンプト

```
以下のエラーが出ています。
[エラーメッセージ全文をコピペ]

考えられる原因を3つ挙げてから、修正してください。
```

「原因を3つ挙げてから」という一文を入れると、Claude Codeが少し立ち止まって考えてくれる感じがあります。

いきなり修正させると「とりあえずこれで」という雑な対応になることがある。原因を言語化させることで、的外れな修正が減りました。

---

### レビュー・リファクタプロンプト

```
現在の[ファイル名]のコードをレビューしてください。
チェック項目：
- セキュリティ上の問題
- パフォーマンスの問題
- 可読性の問題

問題があれば、修正案を提示してください。
（自動で修正はしなくていいです。確認してから修正したい）
```

「自動で修正はしないで」という制限が重要。

私はコードをちゃんと理解してから変更したいので、このフローにしています。特に本番公開前のレビューには必ずこれを使います。

## Claude Codeの指示出しで気をつけていること

実際に6時間半の開発を通じて気づいたコツをまとめます。

**コツ①：一度の指示に含める要件は1〜2個まで**

「音声入力の実装 + スタイルの調整 + エラーハンドリング」を同時に依頼するとカオスになりました。

私は付箋に機能リストを書いて、一個ずつ実装させるようにしています。

**コツ②：「最新バージョンで動くように」は最初に言う**

```
# プロジェクト前提条件
- 2024年時点の最新の書き方で実装すること
- deprecated なメソッドは使わないこと
- コメントは日本語で書くこと
```

CLAUDE.mdというファイルにこれを書いておくと、セッションをまたいでも毎回参照してくれます。

**コツ③：「なぜそうするか」を説明させる**

```
この実装方法を選んだ理由を一言で説明してから実装してください。
```

これを入れると、後から「なぜこの書き方なんだろう」と迷わなくなります。学習にもなる。

**コツ④：途中でセーブする**

Gitのコミットをこまめにやる、ということです。

Claude Codeが大きな変更を加えた後は必ずコミット。万が一おかしくなっても戻れる状態を保っておく。

これを怠って、1時間分の作業が吹き飛んだことがあります。

## Vercelへのデプロイ手順と詰まりポイント

フロントエンドのみのアプリであれば、Vercelへのデプロイは10分で終わります。

手順はシンプル：

1. GitHubにリポジトリを作ってpush
2. Vercel（vercel.com）にGitHubでログイン
3. 「Add New Project」でリポジトリを選択
4. 設定はほぼデフォルトのままDeploy

ここで詰まりやすいのが「環境変数の設定」です。

今回のアプリはユーザーがAPIキーを入力する形式だったので不要でしたが、バックエンドAPIを使う場合はVercelのダッシュボードで環境変数を設定する必要があります。

VercelのUI上で：
`Settings → Environment Variables → Key / Value を入力`

これをしないまま「なぜか本番で動かない」ことになるので要注意。

## 個人開発を「続けられる規模」に保つ考え方

6時間半でリリースできた一番の理由は、機能を削ぎ落としたことです。

最初の企画段階では10個以上の機能を思いついていました。

- 地図連携
- 写真添付
- SNSシェア機能
- タグ管理
- お気に入り機能
- 検索機能
- …

全部やりたかった。でも全部入れたら開発が終わらない。

個人開発が続かない理由のほとんどが「スコープが大きすぎること」だと思っています。

私がやるようになったのは「3つの機能ルール」です。

**コア機能：1つ**（これがないとアプリとして成立しない）
**あったら便利機能：2つまで**（絶対に必要ではないが、UXが上がる）
**これ以外は全部v2以降**

今回で言えば：
- コア機能：音声入力してAIで整形
- あったら便利：保存して一覧表示、データ削除
- v2以降：地図連携、タグ、写真添付…

このルールを決めてから、開発が圧倒的に楽になりました。

## 最初にやること、3ステップ

Claude Codeを使って個人開発を始める人に、最初にやってほしいことを3つだけ書きます。

**Step1：小さすぎるくらいのアイデアを選ぶ**

「これ小さすぎるかな」と思うくらいがちょうどいい。音声レビューツールなんて、考えようによっては「メモ帳」と大差ない。でも自分が使いたいものを作ることが大事。

**Step2：CLAUDE.mdを最初に作る**

プロジェクトのルートに`CLAUDE.md`というファイルを作って、技術スタック、コーディング規約、プロジェクトの概要を書く。

Claude Codeはこのファイルを自動で読んでくれるので、毎回同じ前提を伝える手間が省ける。

テンプレートはこんな感じ：

```markdown
# プロジェクト概要
[アプリ名]：[一行説明]

## 技術スタック
- フロントエンド：HTML / CSS / Vanilla JS
- バックエンド：なし
- デプロイ：Vercel

## コーディング規約
- コメントは日本語
- 2024年時点の最新の書き方を使う
- deprecated なメソッドは使わない

## 開発方針
- 機能は最小限に保つ
- セキュリティを意識した実装をする
```

**Step3：設計→実装→デプロイを1サイクルで完走する**

最初の1本は「いいものを作ろう」と思わなくていい。

1サイクル完走することが目的。完走する感覚を掴めれば、2本目からは格段に楽になります。

# Claudeで失敗した使い方7パターンと改善策まとめ

---

「なんかうまくいかないな」と思いながら、それでもClaudeを使い続けて1年以上が経ちます。

最初の3ヶ月は正直、「ChatGPTのほうがよかったかも」と何度も思いました。でも失敗を重ねて、ようやくClaudeとの付き合い方がわかってきた感じがします。

この記事は、僕が実際にやらかした失敗パターンを7つ、改善策とセットでまとめたものです。

---

## はじめに：なぜ失敗談を書こうと思ったか

沖縄でサラリーマンをしながら、副業でAI活用の記事を書いたりアプリを作ったりしています。Kindle本も8冊出して、ChatGPTとClaudeは毎日使っている、みたいな生活です。

ClaudeはProプランに課金してから本格的に使い始めました。最初は「Claude良い」「Claude賢い」という情報を見て、とにかく試してみた感じです。

ただ、実際使ってみると「あれ、思ってたより返答が微妙だぞ」という場面が何度もあって。原因を調べてみると、ほぼ全部自分の使い方の問題でした。

Claudeの特性をちゃんと理解せず、ChatGPTと同じノリで使ってたのが間違いでした。

---

## 失敗パターンの全体像

7つの失敗を一覧にすると、こんな感じです。

- パターン1：役割を与えずに使っていた
- パターン2：長文を一気に貼り付けていた
- パターン3：「いい感じに」という曖昧な指示を連発していた
- パターン4：会話を長く続けすぎていた
- パターン5：否定形で指示していた
- パターン6：出力形式を指定していなかった
- パターン7：CLAUDE.mdを使っていなかった

パターン1〜3の解説と改善策を無料パートで書きます。パターン4〜7は有料パートで詳しく解説します。

---

## パターン1：役割を与えずに使っていた

### やらかし内容

副業のブログ記事を書くとき、いきなり「〇〇について記事を書いて」と投げていました。返ってくる文章は、無難で当たり障りない内容ばかり。「誰でも書けそうな文章だな」という印象でした。

ChatGPTでも同じ使い方をしていたんですが、Claudeはより「与えられた文脈に忠実」な動きをします。役割が曖昧だと、Claudeも迷うようです。

### 改善策

最初に「あなたは〇〇の専門家です」という役割設定をするだけで、出力の精度が変わります。

具体的に言うと、ブログ記事の作成でこういう書き出しに変えました。

```
あなたはAIツールを活用した副業に詳しいライターです。
実体験ベースで、難しい言葉を使わずに書くスタイルが得意です。
読者は30代の会社員で、副業に興味はあるけどまだ始めていない人です。
```

この3行を加えるだけで、出力のトーンと内容の深さが変わりました。体感で文章の「使える率」が50%から80%くらいに上がった感じです。

---

## パターン2：長文を一気に貼り付けていた

### やらかし内容

Claudeのコンテキストウィンドウが大きい（最大200Kトークン）という話を聞いて、「じゃあ何でも全部貼ればいいじゃん」という誤解をしていました。

たとえば、5万字くらいのドキュメントをそのまま貼って「要約して」と指示していた時期があります。返ってくる要約が、なんか的外れなことが多くて困っていました。

### 改善策

コンテキストが長くなるほど、Claudeは「どこに注目すればいいか」がぼやけます。長文を渡すときは、読んでほしい箇所と目的を明示する必要があります。

改善後の指示の例です。

```
以下のドキュメントから「コスト削減に関する箇所だけ」を抜き出して、
箇条書きで3点にまとめてください。
目的は社内会議での報告用です。
---
[ここにドキュメント貼り付け]
```

「全部読んで何かして」より、「ここだけ見てこうして」のほうが精度が上がります。

長文処理の場合、「何のために要約するか」を書くと、さらに使えるアウトプットになります。

---

## パターン3：「いい感じに」という曖昧な指示を連発していた

### やらかし内容

Kindleの原稿を書くとき、「もう少しいい感じに修正して」「読みやすくして」という指示を繰り返していました。Claudeが修正してくれるんですが、自分が求めている方向と微妙にズレる。そこでまた「もっとやわらかい表現で」とか言う。これを5往復くらいやっていました。

時間のムダだし、Claudeも（たぶん）困っていたと思います。

### 改善策

「いい感じ」という言葉を使わないルールを自分に課しました。代わりに、修正の軸を具体的に書くようにしています。

```
以下の文章を修正してください。
条件：
- 一文を40字以内に収める
- 難しい専門用語は使わない
- 語尾は「〜です」「〜ます」に統一する
- 読み手は副業初心者を想定する
```

修正の指示を数値や条件で書くと、Claude側の解釈のブレが減ります。「いい感じ」という言葉は、自分の中でも言語化できていないサインです。まず自分が何を求めているかを言葉にする、という作業がセットになります。

## ここまでのまとめ（無料パート）

パターン1〜3を整理すると、根本的な問題は「Claudeに文脈を渡せていなかった」ことでした。

- 誰として答えてほしいか（役割）
- どこに注目してほしいか（範囲）
- どんな状態にしてほしいか（具体的な条件）

この3つを先に書くだけで、Claude側の動きが変わります。ChatGPTより指示に対して素直に反応するぶん、こちらの指示が曖昧だとそのまま曖昧な出力が返ってきます。

## パターン4：会話を長く続けすぎていた

### やらかし内容

Claudeのチャット画面で、1つのスレッドを何日もかけて使い続けていました。「文脈を引き継いでくれるから便利」と思っていたんですが、会話が50往復を超えたあたりから、明らかに初期の指示を忘れてきます。

「最初に言ったスタイルで書いて」という指示を無視したような文章が返ってきたり、前半で確認したはずの前提をまた聞いてきたり。

長いスレッドの後半になると、Claudeは文脈の全体を正確に保持しきれなくなることがあります。コンテキストウィンドウは大きいですが、「すべての情報に同等に注目できるか」は別の話です。

### 改善策

**作業ごとに新しいスレッドを立てる**ことにしました。

1つのスレッドで完結させる作業の単位を小さくするイメージです。「今日はこの章の執筆だけ」「この機能のコードレビューだけ」という感じで、セッションを区切ります。

そして毎回スレッドの冒頭に、自分のプロフィールや作業の前提をまとめたテキストを貼り付けるようにしています。10行くらいの「作業開始テンプレート」を用意しておいて、毎回コピペするだけです。

これで「また説明するの面倒くさい」という問題も解決しました。

```
【作業開始テンプレート（例）】
私について：沖縄在住の会社員。副業でAI活用の記事とKindle本を書いています。
今日の作業：note記事の構成案を作る
ターゲット読者：30〜40代の副業に興味がある会社員
文章スタイル：一文60字以内、です・ます調、具体的な数字を入れる
禁止ワード：「革命」「最強」「爆速」などの誇張表現
```

## パターン5：否定形で指示していた

### やらかし内容

「難しい言葉を使わないで」「長くしないで」「箇条書きにしないで」という否定形の指示を多用していました。

実際に試してみると、否定形の指示はClaudeが守れないことが多いです。「使わないで」という指示より「〜を使って書く」という肯定形の指示のほうが、期待通りの出力になります。

これは人間への指示でも同じですが、「〜しないで」より「〜してほしい」のほうが相手は動きやすいです。

### 改善策

指示を書くときに「否定形を使わない」ルールを自分に設けました。

変換の例を3つ書きます。

| 変更前（否定形） | 変更後（肯定形） |
|----------|----------|
| 難しい言葉を使わないで | 中学生でもわかる言葉を使って |
| 長くしないで | 全体で300字以内に収めて |
| 箇条書きにしないで | 文章形式で段落を分けて書いて |

「〜しないで」という禁止指示を減らして、「〜してほしい」という形で書き直すと、一致率がかなり上がりました。体感で往復回数が半分以下になった感じです。

## パターン6：出力形式を指定していなかった

### やらかし内容

「〇〇について教えて」と聞くだけで、出力形式を何も指定していませんでした。ある日は箇条書きで返ってきて、ある日は長文で返ってきて、毎回形式がバラバラ。

特にアプリ開発でAPIを使っているときに困りました。出力をプログラムで処理したいのに、Claudeが気を利かせて「補足説明」を入れてくる。JSONで返してほしいのに、Markdownのコードブロックに包まれてくる、みたいなことが何度もありました。

### 改善策

プロンプトの最後に「出力形式」のセクションを必ず追加するようにしました。

**日常使いの例**

```
以下の質問に答えてください。
出力形式：
- 見出しなし
- 箇条書き3点のみ
- 各項目は1行以内
```

**API連携の例**

```
以下の情報を分析して結果を返してください。
出力形式：
- JSONのみ出力すること
- Markdownコードブロックで囲まないこと
- 補足説明は不要
- キー名はすべて英語のスネークケース
```

出力形式を明示するようになってから、後処理のエラーがほぼなくなりました。特にAPI経由でClaudeを使っているときは、出力形式の指定は必須だと思っています。

## パターン7：CLAUDE.mdを使っていなかった

### やらかし内容

これが一番「知ってればよかった」と思った失敗です。

Claude Codeを使い始めた最初の2ヶ月、毎回プロジェクトの説明を最初から書いていました。「このアプリはReactで作っています」「状態管理はZustandを使っています」「コメントは日本語で書いてください」という内容を、毎セッションのたびに説明していました。

完全に時間のムダでした。

### CLAUDE.mdとは何か

Claude Codeには「CLAUDE.md」というファイルをプロジェクトのルートに置くと、セッション開始時に自動で読み込んでくれる機能があります。いわば「Claudeへの引き継ぎ書」です。

### 実際に使っているCLAUDE.mdの例

僕が個人開発しているWebアプリのCLAUDE.mdを（一部省略して）公開します。

```markdown
# プロジェクト概要
沖縄在住の個人開発者が作るWebアプリです。
タスク管理ツールで、Next.js + Supabaseで構築しています。

## 技術スタック
- フロントエンド：Next.js 14（App Router）
- 認証：Supabase Auth
- DB：Supabase（PostgreSQL）
- スタイリング：Tailwind CSS
- 状態管理：Zustand

## コーディングルール
- コメントは日本語で書く
- 関数名・変数名は英語のキャメルケース
- 型定義は必ずTypeScriptで書く
- コンポーネントは1ファイル1コンポーネント

## 禁止事項
- any型の使用
- console.log（debuggingのみ許可、コミット前に削除）

## よく使うコマンド
- 開発サーバー：npm run dev
- ビルド：npm run build
- 型チェック：npm run type-check
```

このファイルを置いてから、毎回同じ説明をする手間がなくなりました。セッションをまたいでも、Claudeがプロジェクトの文脈を理解した状態でスタートしてくれます。

Claude Code以外でも、系統的にClaudeを使うなら「毎回説明すること」をファイルにまとめておく発想は応用できます。

## 7パターンの改善策まとめ

最後に一覧で整理します。

| パターン | 失敗内容 | 改善策 |
|--------|--------|--------|
| 1 | 役割設定なし | 最初に専門家としての役割を3行で書く |
| 2 | 長文を丸ごと貼る | 読んでほしい箇所と目的を明示する |
| 3 | 曖昧な修正指示 | 条件を数値・形式で具体化する |
| 4 | スレッドを使い続ける | 作業ごとに新スレッド＋開始テンプレ |
| 5 | 否定形で指示する | 肯定形に変換して書く |
| 6 | 出力形式を指定しない | プロンプト末尾に出力形式を書く |
| 7 | CLAUDE.mdを使わない | プロジェクトの引き継ぎ書を作る |

---

## おわりに

Claudeは「賢いAI」ですが、「何でもわかってくれるAI」ではありません。人間と同じで、文脈が整っていれば良い仕事をしてくれるし、文脈が曖昧だと曖昧な答えが返ってきます。

僕がこの1年で学んだのは「Claudeのせいにする前に、自分の指示を疑え」ということです。

失敗のほとんどは、自分の指示の設計の問題でした。

今回の7パターンを一度試してみると、Claudeとの付き合い方が変わると思います。全部一気にやる必要はないので、まず「役割設定」と「出力形式の指定」だけ試してみてください。それだけでも体感が変わります。

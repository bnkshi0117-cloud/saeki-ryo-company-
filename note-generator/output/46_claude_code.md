# CLAUDE.mdの書き方で開発速度が変わる話

---

## 最初に正直に言います

Claude Codeを使いはじめた当初、CLAUDE.mdのことは完全に無視してました。

「どうせ設定ファイルでしょ」と思って、ひたすらチャットで指示を出し続けてたんです。その結果、毎回同じような説明をClaudeに繰り返すことになって、「あれ、これさっきも言ったよな…」という状態が続きました。

CLAUDE.mdをちゃんと書くようにしてから、同じ作業が体感で40%くらい速くなりました。数字にすると、1機能あたりの実装サイクルが平均90分から55分くらいに縮まった感じです。

この記事では、CLAUDE.mdの書き方と、自分が試行錯誤してたどり着いた構成を具体的にまとめます。

---

## CLAUDE.mdって何者なのか

Claude Codeを使ってる人は知ってると思いますが、一応説明します。

CLAUDE.mdは、プロジェクトのルートディレクトリに置くMarkdownファイルです。Claude Codeを起動したとき、このファイルの内容が自動的に読み込まれます。

つまり、**Claudeへの「このプロジェクトの前提知識」をあらかじめ渡しておける仕組み**です。

人間に例えると、新しいバイトが初日に渡される「引き継ぎマニュアル」みたいなものです。これがあるとないとでは、作業の入り方がまったく違う。

自分が最初につまずいたのは、「何を書けばいいかわからない」という点でした。情報が多すぎてもClaudeが混乱するし、少なすぎると意味がない。ちょうどいい量と内容を探るのに2〜3週間かかりました。

---

## CLAUDE.mdがないとどうなるか

実体験の話をします。

以前、家計管理アプリをClaude Codeで作ってたときのことです。CLAUDE.mdを書かずに開発を進めていました。

毎回セッションを開始するたびに、こんな説明をしてました。

- 「このプロジェクトはNext.js 14のApp Routerを使ってます」
- 「データベースはSupabaseで、認証もSupabase Authです」
- 「スタイルはTailwind CSSで、shadcn/uiのコンポーネントを使ってます」
- 「型定義はtypes/フォルダにまとめてあります」

これを毎回打ち込むのに、3〜4分かかってました。1日に5〜6回セッションを開き直すことがあるので、合計で20分以上ロスしてたんです。

しかもこれ、タイピングの時間だけじゃなくて「また書かなきゃいけない」というストレスも地味に積み重なります。

CLAUDE.mdに一度書いてしまえば、それが全部消えます。

---

## 自分が行き着いたCLAUDE.mdの構成

今使ってるCLAUDE.mdの構成を紹介します。5つのブロックで作っています。

**①プロジェクト概要（3〜5行）**

何を作っているアプリか、一言で説明します。ターゲットユーザーと主要機能を書きます。長くならないように注意です。

**②技術スタック**

使ってるフレームワーク、ライブラリ、データベース、認証、デプロイ先をリストで書きます。バージョンも書いておくと、ライブラリの仕様差によるミスが減ります。

**③ディレクトリ構成（簡略版）**

フォルダの役割を簡単に書いておきます。全部書く必要はなくて、「どこに何があるか」がわかる程度で十分です。

**④コーディングルール**

命名規則、コメントの方針、エラーハンドリングの方針などを書きます。「TypeScriptの型定義は必ずつける」とか「console.logは残さない」とか、そういう細かいルールです。

**⑤現在の開発フェーズ・注意点**

今どの段階にあるか、直近でどんな問題が起きているかを書きます。ここだけは定期的に更新しています。

## 実際のCLAUDE.mdサンプル（そのまま使えます）

以下が、自分が現在使っているCLAUDE.mdの雛形です。

括弧の部分を自分のプロジェクトに合わせて書き換えるだけで使えます。

```markdown
# プロジェクト名

## 概要
[アプリの説明を2〜3文で。何をするアプリか、誰が使うか]

例：
家計管理Webアプリ。20〜40代の個人ユーザーが月ごとの収支を記録・可視化できる。
カテゴリ別グラフ、月次レポート、予算設定機能を持つ。

## 技術スタック
- フレームワーク：Next.js 14（App Router）
- 言語：TypeScript
- スタイリング：Tailwind CSS + shadcn/ui
- データベース：Supabase（PostgreSQL）
- 認証：Supabase Auth
- デプロイ：Vercel
- パッケージマネージャー：pnpm

## ディレクトリ構成
```
src/
├── app/          # Next.js App Routerのページ
├── components/   # 再利用可能なUIコンポーネント
│   ├── ui/       # shadcn/uiのコンポーネント
│   └── feature/  # 機能別コンポーネント
├── lib/          # ユーティリティ関数、Supabaseクライアント
├── types/        # TypeScriptの型定義
└── hooks/        # カスタムフック
```

## コーディングルール
- TypeScriptの型定義は必ずつける。anyは使わない
- コンポーネントはアロー関数で書く（function宣言は使わない）
- Supabaseへのアクセスはlib/supabase.tsのクライアントを使う
- エラーハンドリングは必ずtry-catchで書く
- console.logはデバッグ後に必ず削除する
- コメントは日本語でOK

## 命名規則
- コンポーネントファイル：PascalCase（例：TransactionList.tsx）
- 関数・変数：camelCase（例：fetchTransactions）
- 型定義：PascalCase + 末尾にType（例：TransactionType）
- CSSクラス：Tailwindのクラスをそのまま使う

## Supabaseテーブル構成
- users：ユーザー情報（Supabase Authと連携）
- transactions：収支データ（id, user_id, amount, category, date, note）
- categories：カテゴリマスタ（id, user_id, name, color, icon）

## 現在の開発フェーズ
MVP段階。基本的なCRUD機能は完成済み。
現在はグラフ表示機能を実装中。

## 注意点
- Row Level SecurityをSupabaseで設定済み。必ずuser_idでフィルタリングすること
- 日付の扱いはdayjs統一（date-fnsは使わない）
- 金額は常に整数で扱う（円単位、小数点なし）
```

## 5つの「書き方のコツ」

実際に使ってみてわかったことを書きます。

### コツ1：最初から完璧を目指さない

CLAUDE.mdは「育てるもの」です。最初は技術スタックと概要だけでも十分です。開発を進めながら、「これClaudeに毎回説明してるな」と気づいたことを追加していくのが自然なやり方です。

自分の場合、最初に書いたのは10行くらいでした。今は50〜60行になっています。

### コツ2：「なぜそうするか」を書く

ルールだけ書いても、Claudeはその意図を理解できないことがあります。

例えば「dayjs統一」と書くだけより、「日付の扱いはdayjs統一（date-fnsはすでにインストール済みだが使わない）」と書く方が、間違えた提案が来にくくなります。

背景がわかると、類似のケースでも正しい判断をしてもらいやすいです。

### コツ3：テーブル構成は必ず書く

これ、かなり効いてます。

データベースのテーブルと主要カラムをCLAUDE.mdに書いておくと、Claudeが提案するSQLやSupabaseのクエリの精度が上がります。毎回「このテーブルはこんな構造です」と説明しなくて済む。

カラム名のtypoによるバグも減りました。

### コツ4：「やってはいけないこと」を書く

ポジティブなルールより、ネガティブなルールの方が効果的なことがあります。

「anyは使わない」「console.logは残さない」「date-fnsは使わない」のように、禁止事項を明記しておくと、Claudeが間違った方向に提案してくることが減ります。

自分が実際に困った経験がある項目を書いておくのがポイントです。

### コツ5：現在の状況を定期的に更新する

CLAUDE.mdの中で唯一、こまめに更新が必要なのが「現在の開発フェーズ・注意点」のセクションです。

「今日はこの機能を実装する」という情報をここに書いておくと、Claudeがコンテキストを理解した状態で作業に入れます。毎朝作業前に2〜3行更新するだけで、最初のやり取りが減りました。

## よくある失敗パターン

自分がやってしまったミスを共有します。

**失敗1：情報を詰め込みすぎた**

最初に「完璧なCLAUDE.mdを作ろう」と思って、100行以上書いたことがあります。逆効果でした。

情報が多すぎると、Claudeが重要な部分を見落とすことがあります。「全部大事」は「全部重要度が同じ」という意味になってしまう。今は50〜60行を上限の目安にしています。

**失敗2：バージョンを書かなかった**

Next.jsのバージョンを書いてなかったとき、Pages RouterとApp Routerを混在させたコードを提案されたことがあります。

メジャーバージョンが変わるライブラリは特に、バージョンを明記した方がいいです。

**失敗3：更新を怠った**

技術スタックを途中で変更したのに、CLAUDE.mdを更新しなかったことがあります。古い情報を元に提案されて、混乱しました。

スタックを変えたときは、その日のうちにCLAUDE.mdも更新するようにしています。

---

## 実際の変化（数字で）

CLAUDE.mdをちゃんと書くようになってから、何が変わったか。

- セッション開始時の「前置き説明」：平均4分 → 0分
- 1機能の実装サイクル（指示→確認→修正→完成）：平均90分 → 約55分
- 「これじゃない」という的外れな提案の頻度：体感で半分以下

特に効いたのは「Supabaseのテーブル構成を書く」でした。これだけで、クエリ系のやり取りが明らかに減りました。

開発速度というより、「無駄なやり取りが減る」という感覚が近いです。

---

## まとめ

CLAUDE.mdは「書いた分だけ返ってくる」ファイルです。

最初は5分で書ける最小限の内容から始めて、開発しながら育てていくのが現実的なやり方です。完璧なものを最初から作ろうとするより、「毎回説明してるな」と感じた内容を追加するループの方が続きます。

この記事で紹介したサンプルをベースに、自分のプロジェクトに合わせてカスタマイズしてみてください。

「CLAUDE.mdってこういうものだったのか」という理解だけで、使い方がだいぶ変わるはずです。

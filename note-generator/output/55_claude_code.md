## SNS運用、もう手作業に戻れない

毎朝、投稿のネタを考えて、文章を書いて、画像を用意して——。

副業でX（旧Twitter）を運用してた去年の自分は、それだけで1〜2時間が消えてた。

「このルーティン、ちょっとおかしいな」と気づいたのがClaude Codeを触り始めたころで。自分で作ったSNS運用ツールが今、毎朝その作業の大半を肩代わりしてくれてます。

今回はそのツールを作った話を、コストも失敗談も全部ひっくるめて書きます。

## 自己紹介的なもの

沖縄在住の会社員、佐伯亮です。

プログラミングは独学で触ってきた程度で、仕事でコードを書いたことはありません。Kindle本を8冊出して、Webアプリを2本リリースして、副業のほとんどはAIと組み合わせた何かしら、という感じです。

Claude Codeを本格的に使い始めたのは今年の春ごろ。最初は「なんか強いCLIツールらしい」くらいの認識でした。

## Claude Codeって何者か、改めて整理する

ChatGPTやClaudeのWeb版と違うのは、「ターミナルから操作する」点です。

ローカルのファイルを直接読み書きして、コードを生成して、実行まで自律的にやってくれる。「エージェント型の開発ツール」と説明されることが多いです。

Web版のAIでコードを出してもらうのと何が違うかというと——

- ファイル間の関係性を把握した上でコードを書いてくれる
- 「この関数を修正して」「テスト書いて」を1セッションで繋いでいける
- CLAUDE.mdに指示を書いておくと、毎回前提を説明しなくていい

自分が一番感じた違いは「文脈が繋がったまま作業が続く」ことでした。Web版だと「ここはさっきの話と繋がってるんですが…」という補足が必要になる場面が、Claude Codeだとかなり減る。

## なぜSNS運用ツールを作ろうと思ったか

去年まで使ってた運用フローはこんな感じでした。

1. ネタ帳を眺めてテーマを決める（15分）
2. ChatGPTで下書きを作る（10分）
3. 手直しして投稿文を完成させる（20分）
4. 別タブでハッシュタグを調べる（10分）
5. 投稿（数分）

合計1時間前後。毎日これをやってたんですが、ある日「なんでClaude Codeで自動化してないんだろう」と素朴に思いまして。

やりたいことの解像度を上げてみると：

- ネタリストから今日のテーマを自動提案してほしい
- 投稿文の下書きを自動生成してほしい
- 文体チェック（自分のトーンかどうか）を自動でやってほしい
- 出力結果をmarkdownファイルで保存してほしい

この4点があれば、「考える時間」を大幅に削れると判断しました。

---

## 実際に作ったものの全体像

最終的にできあがったのは、Pythonスクリプト1本 + Claude API。

実行するとこうなります。

```
$ python sns_runner.py

📋 今日のテーマ候補を生成中...
→ 1. AI副業で最初の1万円を稼いだ方法
→ 2. Claude Codeで詰まった話とその解決策
→ 3. 沖縄でフルリモート副業は成立するか

番号を選んでください（1-3）: 2

✍️ 下書き生成中...
──────────────────────────
Claude Codeで詰まった話をします。

...（投稿文が出力される）

──────────────────────────
✅ output/2025-07-11.md に保存しました
```

シンプルです。派手な機能はない。でも「毎朝1時間かかってた作業が15分になった」のは事実で、それで十分でした。

## つまずいたポイント（正直に書く）

開発中に「あれ？」となった場面は何度もありました。

**1. Claude Codeに「何でもやってくれ」と丸投げしたら迷子になった**

最初のプロンプトが「SNS運用を自動化するPythonスクリプトを作って」だったんですが、出てきたコードが想定と全然違うものでした。

機能は合ってるんですが、ファイル構成がやたら複雑で、自分が後から読めない。

「ミニマムに、自分が読めるコードで」という制約を最初に入れるべきでした。これ、最初の1〜2時間の教訓です。

**2. APIキーの扱いでハマった**

.envファイルの使い方を曖昧に理解したまま進んでたら、APIキーを直書きしたコードをGitHubにあげそうになった。Claude Codeが「.gitignoreに.envを追加してください」と言ってくれたおかげで気づきましたが、ヒヤッとしました。

**3. 文体チェック機能が「なんか違う」判定ばかりした**

自分の文体サンプルを3つ渡して「このトーンかどうか判定して」という機能を作ったんですが、精度が低くて。結局この機能は簡略化して、「チェックリスト式」に切り替えました。完璧なものを作ろうとするより、動くものを使い続ける方が現実的、という学びです。

## Claude Codeとのやりとりで気づいたこと

3日間作業して、一番変わったのは「指示の出し方」への意識でした。

具体的に変えたこと：

- 「〜してください」より「〜の機能をXXという形式で実装してください」
- 一度に複数機能を頼まない（1機能ずつ）
- 「さっきのコードを確認してから」と明示的に言う
- 完成したら「テストケースを書いてもらえますか」とセットで頼む

Claude Codeは文脈を保持してくれますが、「このコードが正しく動くかどうか」の判断は人間がする必要があります。自分がコードを全部読めなくても、「ここの動作確認をして」と聞けば動作検証も手伝ってくれる。

作る人と確認する人、両方が自分でいい。そういう感覚です。

## 有料パート：実際に使った指示文と開発の全工程

### CLAUDE.mdに何を書いたか

まず、プロジェクトのルートに置いたCLAUDE.mdの中身を公開します。

CLAUDE.mdはClaude Codeに「毎回この前提で動いてね」と伝えるファイルです。これがあると、セッションをまたいで同じ前提からスタートできます。

```markdown
# SNS運用ツール プロジェクト

## 目的
毎朝のX（旧Twitter）投稿作業を半自動化するPythonスクリプトを作る。

## 使用技術
- Python 3.11
- Claude API（anthropic SDK）
- dotenv

## ファイル構成
- sns_runner.py : メインスクリプト
- topics.txt : ネタリスト（1行1テーマ）
- output/ : 投稿下書きの保存先（markdownファイル）
- .env : APIキー管理

## コードのルール
- ファイルは1〜2本に絞る。複雑にしない
- コメントは日本語で書く
- エラー処理は最低限でいい（個人用ツールのため）
- 関数単位でシンプルに分ける

## 私のレベル感
Pythonは読める。書けるが遅い。ライブラリの詳細は把握していない。
コードレビューより「動くものを作る」を優先する。
```

このCLAUDE.mdを置いてからは、毎回「自分はPythonがわかるけど詳しくはない」と説明しなくてよくなりました。地味に大きい。

### 実際に投げた指示文（全公開）

**Step 1：骨格を作る**

```
topics.txtからランダムに3テーマを読み込んで表示するスクリプトを作ってください。
ユーザーが番号で選んだら、そのテーマをprintするだけでOKです。
まずは最小構成で。
```

このときClaude Codeが出してきたコードは30行程度。シンプルで読めた。これが正解だと思います。最初から「全機能まとめて」と頼まなかったのが良かった。

---

**Step 2：Claude APIとの連携**

```
選んだテーマをもとに、Claude APIを使って投稿下書きを生成してください。
文字数は140字以内で。
使用するモデルはclaude-3-5-sonnet-20241022です。
APIキーは.envから読み込んでください。
```

ここで初めて「.envの使い方」が出てきます。Claude Codeが自動で.envの書き方とdotenvのインストール手順も出してくれたので、そのまま実行しました。

---

**Step 3：文体プロンプトの調整**

```
system promptに以下の文体指示を追加してください。

「あなたは沖縄在住の会社員・佐伯亮として投稿します。
特徴：短文。体験ベース。数字を入れる。煽らない。です・ます調。
NGワード：最強・革命・爆速・〜必見・〜だけで」
```

このsystem promptの調整が、ツールの品質に一番影響しました。ここを自分のブランドに合わせて書き込むと、出力が「自分っぽく」なっていきます。

---

**Step 4：出力をファイルに保存**

```
生成した下書きを output/YYYY-MM-DD.md というファイルに保存してください。
ファイルが存在する場合は上書きせず、連番で保存してください（例：2025-07-11_2.md）。
```

このステップでClaude Codeが「outputディレクトリが存在しない場合のエラー処理も追加しますか？」と聞いてきました。こういう「気づき」を出してくれるのもClaude Codeの特徴で、自分が見落とすポイントをカバーしてくれます。

---

**Step 5：ハッシュタグの提案機能を追加**

```
投稿下書きを生成した後、関連するハッシュタグを3つ提案してください。
別のAPI呼び出しで、シンプルなリスト形式で出力します。
```

ここで気づいたのは「API呼び出しを分けると、それぞれの出力品質が上がる」ということです。1回のプロンプトで「下書き+ハッシュタグ」を両方出そうとすると、どちらも中途半端になりがちでした。

### つまずきポイントと解決策（5選）

**① セッションが長くなるとコードの文脈がずれてくる**

症状：新しい機能を追加したら、前の機能が壊れた。

解決策：新機能を追加する前に「現在のsns_runner.pyを読み込んだ上で、以下を追加してください」と明示する。「読み込んだ上で」という一言が大事。

---

**② エラーが出たときにそのままコードを貼ると迷走する**

症状：エラーを貼ったら全然関係ない部分を書き直し始めた。

解決策：「このエラーだけに対応してください。他は変更しないでください」という制約を入れる。Claude Codeは親切なので「ついでに改善」してくることがありますが、それが混乱の原因になります。

---

**③ topics.txtの書き方が雑だとテーマ提案の精度が下がる**

症状：「AI副業」みたいな短いキーワードしか書いてなかったら、下書きが抽象的になった。

解決策：ネタリストを「〜してわかったこと」「〜で詰まった話」という文章形式で書く。テーマが具体的なほど、下書きも具体的になる。

---

**④ APIの応答が遅くてタイムアウトする（稀に）**

症状：生成中に固まった。

解決策：`timeout=60`をAPI呼び出しに追加。これをClaude Codeに頼んだら一発で解決しました。「タイムアウト処理を追加してください」と一行伝えるだけ。

---

**⑤ 出力が「です・ます調」になったり「だ・である調」になったりブレる**

症状：同じsystem promptを使ってるのに文体がバラバラ。

解決策：system promptに「必ずです・ます調で書いてください。だ・である調は使わないでください」と明示的に禁止する。禁止の言い方にするのがポイント。「推奨」より「禁止」の方が安定します。

### 非エンジニアが最初にやるべき順序

自分が最初からやり直すとしたら、この順序でやります。

**1. CLAUDE.mdを先に書く**

プロジェクトの目的・使用技術・自分のレベル感をCLAUDE.mdに書いてから開発を始める。これだけでセッションの精度が上がります。

**2. 最小機能から作る**

「全機能が動く完成品」を目指さない。最初は「動くミニマム版」だけ作る。今回でいうと「テーマ選んで出力するだけ」が最初のゴールでした。

**3. 1機能ずつ追加する**

骨格ができたら機能を1つずつ追加していく。「Step 1ができたら次はAPI連携」という順番を守ると、どこで壊れたかがわかりやすい。

**4. エラーが出たら「この部分だけ」と絞って聞く**

全体を渡してしまうと、関係ないところも変更されてしまう。問題の場所を絞り込んでから聞くのが鉄則。

**5. 動いたらすぐ使い始める**

完璧にしてからではなく、60%の完成度で使い始める。実際に使うと「あ、この機能いらないな」「こっちの方が便利」がわかる。自分のsns_runner.pyも、今も少しずつ変わり続けています。

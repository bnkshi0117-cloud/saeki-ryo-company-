# 個人開発でClaude Codeを使うメリットとデメリット正直レビュー

---

## 「これ、本当に使えるの？」と思いながら試した話

正直に言います。

最初にClaude Codeを触ったとき、「またAIツールが増えたか」くらいにしか思ってませんでした。ChatGPTにコードを書かせる方法は知ってたし、Cursorも使ってた。それと何が違うの？という感覚。

でも2週間ほど個人開発に使ってみて、考えが変わりました。良い意味でも、悪い意味でも。

この記事では、Claude Codeを実際に使って感じたメリット・デメリットを比較しながら正直に書きます。「導入すべきかどうか迷ってる人」が読んで判断できるよう、具体的に書きました。

## 自己紹介（そんなに長くないです）

佐伯亮、沖縄在住の会社員です。

副業でAI活用・Kindle出版・アプリ開発をやってます。Webアプリはこれまでに2本リリースしました。どちらもReact + Supabase構成で、バックエンドはほぼAIに書かせてます。

プログラミングの経験は「ちょっとある」くらい。HTMLとCSSは書けます。JavaScriptは雰囲気で読める。本格的なエンジニアではない、という前提で読んでください。

---

## そもそもClaude Codeって何？

簡単に説明します。

Claude CodeはAnthropicが提供するCLIツールです。ターミナル上で動き、プロジェクト内のファイルを直接読み書きしながらコードを生成・修正してくれます。

CursorやGitHub Copilotがエディタに組み込まれているのに対して、Claude Codeはターミナルで操作するのが特徴です。ファイルの作成・編集・コマンド実行まで、かなり広い範囲を自律的に動いてくれます。

料金はAnthropicのAPIを使う従量課金制。月額固定ではなく、使った分だけ課金されます。

## 比較対象を整理しておく

今回の記事は「Claude Codeを使うべきか」という比較記事です。

比較対象として、自分が実際に使ってきたツールを軸にします。

- **ChatGPT（コードをチャットで生成）**
- **Cursor（エディタ内AI補完）**
- **Claude.ai（ブラウザ版のClaude）**

これら3つとClaude Codeを比較しながら、何が良くて何が微妙だったかを書きます。

## メリット3つ

### ① ファイルをまたいで作業してくれる

これが一番大きかった。

ChatGPTやブラウザ版Claudeにコードを書かせると、「このファイルをこう直して」「あのファイルにこの関数を追加して」と1つずつ指示しないといけません。自分がコードをコピーして貼って、確認して、また次のファイルを渡して…という作業が発生します。

Claude Codeはプロジェクトフォルダを丸ごと見ながら動きます。「このコンポーネントのスタイルをこっちと統一して」と言えば、関連ファイルを自分で確認しながら修正してくれます。

実際に試したとき、3ファイルにまたがる修正を一度の指示でやってもらえました。同じことをChatGPTでやると、少なくとも20分はかかってた作業が5分で終わった感覚です。

### ② コマンド実行まで一貫してやってくれる

ライブラリのインストールからビルド確認まで、ターミナルのコマンドも自分で実行してくれます。

「npm installして、動作確認して、エラーがあれば直して」という流れを人間の確認なしに進めてくれます。もちろん、実行前に確認を求めてくるケースもあります。

Cursorはあくまでエディタ内のAI補完なので、コマンドまで実行してくれるわけではありません。Claude Codeはそこが違います。

### ③ CLAUDE.mdで文脈を保持できる

CLAUDE.mdというファイルをプロジェクトのルートに置くと、毎回読み込んでくれます。

「このプロジェクトはTypeScript + React + Supabaseで作ってる」「コンポーネントはsrc/components/以下に置く」「スタイルはTailwindを使う」といった情報を一度書いておくと、毎回説明しなくていい。

これは地味だけど効いてきます。ChatGPTにコードを書かせると「毎回プロジェクトの構成を説明する」手間があります。Claude Codeはそれがない分、指示の文章が短くなる。

## デメリット3つ

### ① 料金の見通しが立ちにくい

これは正直、使い始めて一番モヤッとした部分です。

従量課金なので、1セッションでいくら使ったか把握しにくい。試しに1時間ほどガッツリ作業したら、予想より多くトークンを消費してました。

Cursorは月額20ドル固定で使い放題のモデルがあります。使い方によってはCursorのほうが結果的に安くなるケースがあります。コストを予測したい人には向いてないかもしれません。

自分の場合、1週間の軽い開発で数ドル程度でした。ただ、複雑なプロジェクトで長時間使うと、その分増えます。

### ② ターミナル操作に慣れてないと入口が高い

Claude Codeはターミナルで動きます。

macであればターミナル.appやiTerm2、WindowsならWSL（Windows Subsystem for Linux）かPowerShellで動かします。最初のインストールも`npm install -g @anthropic-ai/claude-code`という形でCLIツールとして入れます。

Cursorはエディタをダウンロードして起動するだけ。Claude Codeはそこから少し手間がかかります。

非エンジニアの人だと、この入口でつまずく可能性があります。自分はターミナルに多少慣れてたので問題なかったけど、「ターミナルって何？」という段階だと別の壁が出てきます。

### ③ 大きすぎるタスクを渡すと迷子になる

「このアプリ全部作って」みたいな丸投げをすると、途中から方向性がズレてくることがあります。

Claude Codeはコンテキスト（会話の長さ）に限界があります。長い作業を一度に任せると、最初に決めた方針を忘れたり、違うアプローチで書き直したりし始めます。

これはChatGPTでも同じ問題ですが、Claude Codeで長時間作業をするとより顕著に出ます。タスクを細かく分けて渡すのが正解で、「まず○○を実装して」「次に△△を追加して」という形で刻んで指示する必要があります。

## 結局、誰に向いてるのか

自分なりに整理するとこうです。

**Claude Codeが向いてる人**
- すでにプロジェクトがあって、特定の機能追加や修正をしたい
- ターミナルに多少慣れてる
- 複数ファイルをまたいだ作業が多い
- API課金のコントロールができる

**Cursor or ChatGPTのほうが合いそうな人**
- ゼロからアプリを作り始める段階
- ターミナルが苦手
- 月額固定で費用を管理したい
- エディタで作業しながらAIに聞きたい

どちらが「勝ち」とかではありません。使うシーンが違います。

自分は今、既存プロジェクトの修正・機能追加でClaude Codeを使って、新規プロジェクトの立ち上げはCursorでやる、という使い分けに落ち着いています。

## 実際に使った指示文（プロンプト）の例

Claude Codeへの指示の出し方にはコツがあります。

ChatGPTへの指示と似ているようで、少し違う。Claude Codeはプロジェクト全体を見ているので、「前提を全部説明する」必要がありません。むしろ説明しすぎると長くなって、ノイズになります。

自分が実際に使った指示文を5つ、そのまま公開します。

---

**指示文① ：コンポーネントの新規追加**

```
src/components/にUserCardコンポーネントを作って。
表示する情報は名前・アバター画像・登録日。
スタイルはすでにあるPostCardコンポーネントと同じ雰囲気で。
Tailwindを使ってください。
```

ポイントは「既存のコンポーネントと同じ雰囲気で」という部分。Claude Codeは既存ファイルを読めるので、デザインの参照元を指定するだけでスタイルを合わせてくれます。色コードやclassを全部書く必要がない。

---

**指示文② ：APIの修正**

```
src/lib/api.tsのgetUserData関数がエラーを返すことがある。
Supabaseのレスポンスがnullのときに落ちてる気がする。
null チェックを追加して、空オブジェクトを返すように直して。
```

エラーの原因を「気がする」レベルで書いても、Claude Codeが実際のコードを読んで確認してくれます。「落ちてる箇所を探して」という丸投げより、「ここが怪しい」という仮説を伝える方が精度が上がりました。

---

**指示文③ ：機能追加（ファイルをまたぐケース）**

```
投稿一覧ページに検索バーを追加したい。
- 入力した文字でタイトルをフィルタリング
- リアルタイムでフィルタされる（APIを叩かない、フロントのみ）
- 既存のレイアウトを崩さないように

関係するファイルを確認して実装して。
```

「関係するファイルを確認して」という一文が効きます。自分がどのファイルを触ればいいかわからなくても、Claude Codeが探して対応してくれます。

---

**指示文④ ：デプロイ前の確認**

```
Vercelにデプロイする前に確認してほしいことがある。
- TypeScriptのエラーがないか
- 未使用のimportが残ってないか
- console.logが残ってないか
チェックして、問題があれば修正して。
```

これは特に便利でした。デプロイ直前のチェックリストをそのまま指示文にする使い方です。人間がやると20〜30分かかる確認を、5分以内にやってくれます。

---

**指示文⑤ ：リファクタリング**

```
src/pages/dashboard.tsxが500行超えてて読みにくい。
コンポーネントに分割して、src/components/dashboard/以下に置いて。
ロジックは変えないで、見た目の動作は同じままにして。
```

「ロジックは変えないで」という制約を入れるのが重要です。これを言わないと、Claude Codeが改善しようとして別の実装に変えてしまうことがあります。

## CLAUDE.mdに書いておくと効果的な内容

CLAUDE.mdはプロジェクトの「取扱説明書」です。

毎回の指示から省ける情報を書いておく場所です。自分が実際に使っているCLAUDE.mdのテンプレートを公開します。

```markdown
# プロジェクト概要
[アプリ名]のWebアプリ。[一言で何をするアプリか]。

# 技術スタック
- フレームワーク：React（TypeScript）
- スタイリング：Tailwind CSS
- データベース：Supabase
- デプロイ：Vercel

# ディレクトリ構成
- src/components/ : 再利用するコンポーネント
- src/pages/ : ページ単位のコンポーネント
- src/lib/ : APIやユーティリティ
- src/hooks/ : カスタムフック

# コーディングルール
- 型定義は必ずつける（anyは禁止）
- コンポーネントは関数コンポーネントで書く
- console.logは残さない
- コメントは日本語で書く

# 注意事項
- Supabaseの接続情報は.envにある（直接書かない）
- デプロイはVercel経由なのでpackage.jsonのbuildコマンドを変えない
```

これを置いておくと、「このプロジェクトはTypeScriptで…」という説明が毎回不要になります。

## 途中で迷子になったときのリセット方法

長い作業をしていると、Claude Codeがおかしな方向に進み始めることがあります。

症状として出やすいのはこの2つ。

1. 最初と違う実装アプローチで書き直し始める
2. 自分で作ったファイルを自分で上書きしてループする

こうなったときのリセット方法です。

**方法① ：Ctrl+Cで止めて、指示を整理する**

まず止めます。続けさせても悪化します。「一旦やめて。今の状況を整理して」と打ち直す。現状確認をさせてから、次の指示を出す。

**方法② ：「今のアプローチで問題ないか確認して」と聞く**

Claude Codeは自分のアプローチに疑問を持たないことがあります。外から「その方法で合ってる？」と聞くと、自分で問題に気づいて修正案を出してくれることがあります。

**方法③ ：新しいセッションで、問題のファイルだけ渡す**

コンテキストが長くなりすぎたときに有効です。新しいセッションを始めて、「このファイルだけ見て、この問題を直して」と最小限の情報で再スタートします。

## コストを抑えながら使うコツ

課金の仕組みを理解すると、コストコントロールがしやすくなります。

Claude Codeのコストはトークン数に比例します。入力（指示文 + 読み込むファイル）と出力（生成するコード）の合計です。

コストを下げるためにやっていること：

**大きすぎるファイルを渡さない**
500行以上のファイルを丸ごと渡すとトークンを多く消費します。「このファイルの〇〇の関数だけ」という形で範囲を絞ると節約できます。

**不要なファイルをignoreする**
`.claudeignore`ファイルを作って、node_modulesやビルド済みファイルを除外します。これだけでかなりトークンが変わります。

```
node_modules/
.next/
dist/
.git/
```

**確認作業はブラウザ版で済ませる**
「このコードの意味を教えて」「このエラーの原因は？」という質問系は、ブラウザ版Claude.aiで無料枠を使う。Claude Codeは実際にファイルを変更するときだけ使う、という使い分けが効果的です。

## 「これをやると失敗する」パターン3つ

最後に、やってしまいがちな失敗パターンをまとめます。

**失敗① ：「全部作って」とゼロから丸投げする**

Claude Codeは既存のコードを修正するのは得意ですが、ゼロから全部設計するのは苦手です。最初にCursorやv0（UIジェネレーター）でざっくり雛形を作ってから、Claude Codeで機能追加・修正をするのが現実的な流れです。

**失敗② ：エラーメッセージだけ貼り付ける**

「このエラーが出ました。[エラー文]」だけ伝えるのは情報不足です。「どの操作をしたときに出るか」「どのファイルで発生してるか」を一緒に伝えると解決速度が上がります。

自分がよく使う伝え方：
「○○ページで○○ボタンを押したときに以下のエラーが出ます。src/pages/hogehoge.tsxのuseEffectあたりだと思います。[エラー文]」

**失敗③ ：承認なしで進めさせる**

Claude Codeにはファイル編集・コマンド実行の承認を求めるかどうかの設定があります。最初のうちは「全部承認なし」にせず、変更内容を確認しながら進める方が安全です。

大事なファイルを意図せず書き換えられた、ということが実際にありました。gitでバージョン管理しておくのも必須です。

## まとめ

Claude Codeを2週間使って感じたのは、「使いこなせるかどうかは指示の精度次第」ということです。

ツール自体の能力は高い。でも、曖昧な指示を出すと曖昧な結果が返ってきます。これはChatGPTでも同じですが、Claude Codeは自律的に動く分、方向が間違ったときに被害が大きくなる。

逆に言えば、指示の出し方を身につければ、既存ツールよりかなり作業が速くなります。

個人開発でClaude Codeを使うなら、まずは既存プロジェクトの小さな改修から試してみてください。「ここの関数だけ直して」「このコンポーネントに機能を追加して」という小さいタスクで感覚を掴むのが早いです。

沖縄の片隅から、引き続き実体験を書いていきます。

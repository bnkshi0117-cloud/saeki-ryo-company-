## 「AIにコードを書かせる」から「AIに開発を任せる」へ

正直、最初は半信半疑でした。

「Subagentって何が違うの？」と思いながら使ってみたら、30分後には口が開いたまま止まらなかった。

これ、普通のClaude Codeの使い方とは本質的に違う。そう気づいたのは、複数のファイルが自動で書き換えられていく様子をただ眺めていたときです。

---

## 自己紹介と経緯

佐伯亮といいます。沖縄在住の会社員で、副業でWebアプリ開発やKindle出版をやっています。

エンジニアではありません。HTML/CSSは書けるけど、JavaScriptはギリギリ読める程度。Reactのコンポーネント構造は理解しているけど、自分でゼロから書くのはしんどい。そういうレベルです。

Claude Codeを使い始めたのは約4ヶ月前。最初は「便利なコード補完ツール」くらいの認識でした。でも使い込むうちに、Subagent機能の存在に気づいて、使い方が変わった。

今回はその体験を、できるだけ具体的に書きます。

## そもそもSubagentって何？

Claude Codeを使ったことがある人なら、こういう経験があると思います。

「このファイルを直して」と指示すると、Claudeが1つのファイルを修正してくれる。でも関連する別のファイルは触らない。自分でまた「あっちも修正して」と言わないといけない。

これが通常の使い方です。

Subagent機能を使うと、話が変わります。

Claude Codeが「親エージェント」として動いて、サブタスクを複数の「子エージェント」に分散して実行する。それぞれのエージェントが並行して動いて、結果をまとめる。

要するに、1人で頼んでいたことを、チームに投げるような感覚です。

公式では「エージェントオーケストレーション」と呼ばれています。私が初めて使ったのは、あるWebアプリの機能追加をするタイミングでした。

---

## 実際に体験したこと

### ── 使ったプロジェクト

私が開発中だったのは、タスク管理系のWebアプリです。フロントはReact、バックエンドはSupabase、デプロイはVercel。規模としては中くらい。ファイル数は当時60〜70個ほどありました。

そこに「ユーザーごとのダッシュボード機能を追加する」という割と大きめの改修を加えようとしていました。

影響するファイルは体感で10個以上。認証周り、データベーススキーマ、コンポーネント、ルーティング、APIのハンドラー、型定義……。

普通にClaude Codeに頼むと、「まずここを直して」「次にここ」「あ、こっちも」という往復が延々と続きます。1つ直すと別の場所でエラーが出る、そのループです。

### ── Subagentを起動したら何が起きたか

Subagentを使う指示を出すと、Claudeがまず全体を分析し始めました。

「このタスクをサブタスクに分割します」というメッセージが出て、以下のような分割が自動でされました。

- データベーススキーマの変更
- 認証フローの修正
- ダッシュボードコンポーネントの作成
- ルーティングの更新
- 型定義の更新

この5つが、ほぼ並行して処理されていきました。

画面上では、複数のサブタスクが順次実行されている様子が見えます。あるエージェントがスキーマを書き換えている間に、別のエージェントが型定義を更新している。

私がやったことは、最初に一回指示を出しただけ。

30分後、「すべてのサブタスクが完了しました」と表示された。

確認してみると、関連ファイルが整合性を保った状態でまとめて更新されていました。

### ── ここが本当に違う

通常の使い方との差は「整合性」です。

1つずつ修正していくと、前の修正と後の修正が噛み合わないことが起きます。型定義を変えたのにコンポーネントが古い型を使っている、みたいな。

Subagentは、全体像を把握したうえで各サブタスクが動くので、この矛盾が起きにくい。全部終わったあとにエラーが出る確率が、体感で半分以下になりました。

以前は大きめの修正をすると、修正後のデバッグに1〜2時間かかっていました。Subagentを使った修正では、デバッグに使った時間は30分以下でした。

## 使ってみてわかった、向いている作業と向いていない作業

何でもSubagentがいいかというと、そうでもないです。

**向いている作業**

- 複数ファイルにまたがる機能追加
- リファクタリング（特に大規模なもの）
- 新機能のスキャフォールディング（雛形作成）

**向いていない作業**

- 1〜2ファイルの小さな修正
- UIの細かいスタイル調整
- エラーの原因究明（1点集中した方が速い）

小さなタスクにSubagentを使うと、むしろ時間がかかります。分割・並行処理のオーバーヘッドがあるので。

「この機能丸ごとお願い」という粒度のタスクが一番合っています。

## 一度失敗したこと

実は最初、うまくいかなかったケースがあります。

指示が曖昧すぎると、Subagentが勝手な解釈をすることがありました。

「ダッシュボードを作って」とだけ言ったら、私が想定していなかったUIになっていた。サブタスクが全部完了してから気づいたので、修正がまた大変でした。

そこから学んだのは、「Subagentを使うときは、最初の指示をいつもより丁寧に書く」ということです。

全体像、使う技術スタック、UIのイメージ、これを最初にまとめて渡す。そうするとSubagentが適切にサブタスクを設計してくれます。

CLAUDE.mdにプロジェクトの基本情報を書いておくのも効果がありました。毎回説明しなくていい。

---

## 非エンジニアこそSubagentが有効な理由

私がエンジニアじゃないからこそ感じることがあります。

通常のClaude Codeの使い方は、会話を続けながら開発を進めます。「次はここ」「あそこも」と自分が開発の交通整理をするわけです。

でもそれって、ある程度コードが読めて、何がどこに影響するか理解できている前提です。

私みたいに「なんとなく構造はわかるけど全部は追えない」人間には、自分が交通整理をするのは難しい。修正漏れが出る。

Subagentなら、「全体を見て、必要なところを全部やってくれ」と言える。Claudeが交通整理をしてくれる。

これは非エンジニアにとって、地味に大きな違いです。

## 実際に使ったプロンプト（そのまま公開）

以下が、ダッシュボード機能を追加したときにSubagentへ渡した最初の指示文です。

```
このプロジェクトにユーザーダッシュボード機能を追加してください。

## 概要
ログインしたユーザーが自分専用のダッシュボードを見られるようにする。
ダッシュボードには「直近のタスク一覧」「完了率」「今週の活動グラフ」を表示する。

## 技術スタック
- フロントエンド：React（TypeScript）
- バックエンド：Supabase（Row Level Security使用）
- スタイリング：Tailwind CSS
- ルーティング：React Router v6

## 制約
- 既存のsrc/components/layout/ のレイアウト構造を維持する
- Supabaseの既存テーブル（tasks, users）は変更可。外部キー関係を壊さないこと
- モバイル対応が必要（ブレークポイントはsm/md/lgを使う）

## 期待するファイル構成
src/
  components/
    dashboard/
      DashboardPage.tsx
      TaskSummary.tsx
      ActivityGraph.tsx
  hooks/
    useDashboardData.ts
  types/
    dashboard.ts
```

ポイントは3つです。

**①「何を作るか」を箇条書きで明確に書く**

「ダッシュボードを作って」だけだと、Claudeが解釈します。その解釈が合っているとは限らない。表示する内容を具体的にリストアップします。

**②「触ってはいけない部分」を書く**

これを書かないと、Subagentが予想外のところを変更することがあります。「既存の〇〇は変えるな」という制約を入れると、整合性が上がりました。

**③期待するファイル構成を先に書く**

これをやるようになって、生成されたコードの品質が上がりました。どこに何を置くかが明確になるので、サブタスクの分割精度が上がります。

## Subagentを起動するための具体的なコマンド

Claude Codeのインターフェース上でSubagentを使うには、いくつかの方法があります。

**方法1：スラッシュコマンド**

Claude Codeのターミナル内で、

```
/agent
```

と入力すると、エージェントモードに切り替わります。その後に指示を入力します。

**方法2：指示文の冒頭に「エージェントとして」を入れる**

明示的に書くことで、Claudeがサブタスク分割を検討します。

```
エージェントとして、以下のタスクを並行処理できる単位に分割して実行してください。
```

私は両方試しましたが、複雑なタスクでは方法2の方が、最初の分割計画を確認できるので好みです。

## CLAUDE.mdに書いておくべき項目

CLAUDE.mdはプロジェクトのルートに置くファイルです。Claudeが読んで、プロジェクトの文脈を理解します。

私が実際に書いている項目を公開します。

```markdown
# プロジェクト概要
タスク管理WebアプリのMVPです。
個人ユーザーが使うシンプルなツール。

# 技術スタック
- React 18（TypeScript）
- Supabase（認証 + DB）
- Tailwind CSS
- React Router v6
- Vercel（デプロイ）

# ディレクトリ構成
src/
  components/  # UIコンポーネント（atomic designに近い構成）
  hooks/       # カスタムフック
  lib/         # Supabase clientなど外部サービス連携
  types/       # TypeScript型定義
  pages/       # ルーティングの単位となるページコンポーネント

# コーディング規約
- コンポーネントはすべてarrow function
- propsは必ずinterfaceで型定義
- Supabaseの呼び出しはhooks/内にまとめる
- console.logは開発中以外削除

# 触ってはいけない部分
- src/lib/supabaseClient.ts は変更しない
- src/types/global.d.ts は変更しない
- package.jsonのdependenciesは指示なく変更しない

# 現在の課題
（開発中に随時更新）
```

このCLAUDE.mdがあると、毎回同じ説明をしなくていい。特に「触ってはいけない部分」の項目は、Subagent使用時のトラブルをかなり減らしてくれました。

## 失敗から学んだ「最初の指示」の書き方フォーマット

失敗した経験から作ったフォーマットです。コピーして使えます。

```
## タスク概要
（一言で何をするか）

## 背景・目的
（なぜこの機能が必要か）

## 実装する内容
- （機能1）
- （機能2）
- （機能3）

## 技術的な制約
- 使用するライブラリ：
- 変更してはいけないファイル：
- 守るべきコーディング規約：

## 完成イメージ
（ユーザーが操作したときに何が起きるか、動詞で書く）

## 期待するファイル変更
（新規作成するファイル）
- 

（変更するファイル）
- 
```

このフォーマットで書くと、Subagentのサブタスク分割が明確になります。「変更するファイル」を自分でリストアップしておくと、漏れが減ります。

## 実装フロー：ダッシュボード機能を追加した手順

実際にどう進めたか、手順として書きます。

**ステップ1：CLAUDE.mdを更新する（5分）**

プロジェクトに新しく加える機能の情報をCLAUDE.mdに追加しました。「これから追加する機能：ユーザーダッシュボード」という形で。

**ステップ2：指示文を書く（10分）**

上記のフォーマットを使って、Notepadに指示文を書きました。タスク概要から期待するファイル変更まで。

書いているうちに「あ、型定義のファイルも作らないといけないな」と気づくことがあります。Claude Codeに渡す前にこれを整理しておくと、後の修正が減ります。

**ステップ3：Subagentを起動（1分）**

Claude Codeのターミナルを開いて、指示文を貼り付け。

```
エージェントとして、以下のタスクをサブタスクに分割して実行してください。

[指示文をここに貼る]
```

**ステップ4：サブタスク分割の確認（5分）**

Claudeがサブタスクを提示してきます。私はここで内容を確認して、必要なら「このサブタスクを先に実行してほしい」とか「これは後でいい」と伝えることがあります。

問題なければ「実行してください」で開始します。

**ステップ5：実行中は待つ（15〜30分）**

複数のサブタスクが実行されます。私は基本的に待つだけです。ターミナルのログを眺めて、何か変なことが起きていないか確認する程度。

**ステップ6：完了後に確認（20分）**

すべてのサブタスクが完了したら、ローカルで動作確認します。

```bash
npm run dev
```

私の場合、このダッシュボード機能の追加では、最初の動作確認でエラーが2件出ました。どちらもSupabaseのRLS（Row Level Security）のポリシー設定が足りていないものでした。

「このエラーを直して」とClaudeに伝えたら、5分で解消しました。

**トータル時間：約55分**

以前の自分（通常のClaude Codeを使っていた頃）なら、同じ機能追加に3〜4時間かかっていました。

## まとめ：Subagentを使うべき状況と使わなくていい状況

改めて整理します。

**使うべき状況**

- 機能追加で5ファイル以上触る可能性がある
- リファクタリングで複数のコンポーネントを書き直す
- 新機能のスキャフォールディング（最初から作る）

**使わなくていい状況**

- 1つのファイルのバグ修正
- UIのスタイル微調整
- 変数名の変更などの小さい修正

Subagentは「大きいタスクを速く終わらせる道具」です。小さいタスクに使うと、分割と並行処理のオーバーヘッドで遅くなります。

非エンジニアとしては、Subagentの登場で「開発のボトルネックが何か」が変わった感覚があります。

以前は「どこを直せばいいかわからない」が詰まりポイントでした。

今は「最初の指示をいかに丁寧に書くか」が開発品質を左右しています。コードを書くスキルより、タスクを言語化するスキルの方が重要になってきた。

これは非エンジニアにとって、悪くない変化だと思っています。
